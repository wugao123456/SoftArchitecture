## 核心论点

接下来，笔者将结合一体化智能运维平台中"智能对话运维助手（AIOps Copilot）"与"故障案例库处置推荐"两个实际落地场景，从"面向运维领域的知识库构建与文档切分策略"以及"向量检索与私有化大模型融合的检索增强架构"两个方面展开论述。

### 论点一：面向运维领域的知识库构建与文档切分策略

运维领域知识具有来源异构、半结构化、时效性强且与具体应用系统强绑定等特点。平台的 RAG 知识库需覆盖历史告警处置案例、故障根因与 Runbook 预案、CMDB 服务依赖拓扑、运维手册与 SOP、指标口径与规则说明等多类文档，这些数据分散在 ITSM 工单系统、Wiki 知识库、ES 告警库、Neo4j 拓扑库等不同系统中，数据格式与口径差异较大。

在知识库构建环节，我主导设计了"统一采集—清洗归一—元数据标注—向量化入库"的处理流水线：通过数据平台的统一订阅接口从各源系统增量拉取文档，对工单类半结构化数据抽取"故障现象—根因定位—处置步骤"三元组，对 Runbook 按执行步骤原子化拆分，对 CMDB 拓扑数据按服务依赖子图组织；同时为每条知识统一标注应用系统、所属团队、数据中心、告警级别、更新时间等元数据字段，既支撑后续基于 RBAC 的数据权限过滤，也便于按应用、按团队缩小召回范围。

在文档切分环节，由于运维知识具有强场景关联性——例如一条告警处置案例中，阈值配置、故障现象、处置动作三者不可割裂——我们在设计之初曾采用固定 512 Token 长度的一刀切分方式，导致召回片段语义不完整、大模型生成的处置建议缺少前置条件。通过深入分析运维知识的语义结构，我们改为采用"语义边界优先、场景完整性优先"的切分策略：以故障案例、处置预案、指标说明等自然语义单元作为 chunk 边界，仅对超长文档按 1024 Token 切分并保留 128 Token 重叠，同时在 chunk 元数据中挂载应用系统与告警级别标签。切分完成后，采用行内部署的中文 Embedding 模型（BGE-large-zh）生成 768 维向量，连同原文与元数据一并写入 Elasticsearch 的 Dense Vector 字段，构建结构化字段与向量字段的混合索引。

### 论点二：向量检索与私有化大模型融合的检索增强架构

在检索增强生成环节，单一向量检索在运维场景下面临两个突出问题：一是专业术语（如 P99 时延、RPO、TPS 等）字面差异导致关键词召回不足，二是告警处置预案频繁更新后向量索引更新滞后，导致召回到过期方案。为此，我设计了"BM25 关键词检索 + Dense Vector 语义检索 + Reranker 重排序"的混合检索链路。

具体而言，用户通过自然语言提问后，系统并行执行 BM25 关键词检索与 Dense Vector 近似最近邻检索，两路候选集通过 RRF（倒数排名融合）算法合并，再经由轻量 Cross-Encoder 重排序模型选出 TopK 最相关片段；随后将召回片段与用户问题按预设模板组装进 Prompt，调用行内私有化部署的大模型生成回答，告警、指标、拓扑等敏感数据全程不出内网，满足银保监对数据安全的监管要求。

在实施过程中，我们还遇到了两个实际问题并逐一解决。第一，检索结果与问题相关度不高导致大模型出现"幻觉"，生成与实际场景不符的处置建议。对此我们引入反馈闭环机制：运维人员对回答标记"准确/误报/部分准确"，误报样本回流后一方面用于微调重排序模型，另一方面补充专业术语同义词词典与行业词典，逐步提升召回精度。第二，告警风暴场景下历史故障案例更新频繁，但全量重建向量索引耗时长、影响线上服务。对此我们为每个 chunk 设置版本号与时间戳，知识库增量更新时仅对变更文档触发增量向量化，ES 索引采用别名切换实现秒级生效，保障新的处置预案更新后立即可被召回。此外，我们还将检索到的 Top3 处置预案直接挂接在 Runbook 编排引擎上，告警触发时自动推荐并支持一键执行，实现了"检索问答—方案推荐—自动执行"的闭环。

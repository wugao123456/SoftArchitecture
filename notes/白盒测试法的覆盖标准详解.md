# 白盒测试法的覆盖标准详解

白盒测试（又称结构测试、透明盒测试）将程序看作一个透明的盒子，基于程序的内部逻辑结构设计测试用例。其核心思想是：**用不同的覆盖标准来衡量测试的充分程度**。覆盖标准从低到高形成一条强度递增链，强度越高，发现错误的能力越强。

---

## 一、覆盖标准总览（强度递增）

```
语句覆盖 < 判定覆盖 < 条件覆盖 < 判定/条件覆盖 < 条件组合覆盖 < 路径覆盖
```

下面逐一详解每种覆盖标准的定义、示例和特点。

---

## 二、各覆盖标准详解

### 2.1 语句覆盖（Statement Coverage）

#### 定义

设计足够多的测试用例，使得程序中**每条可执行语句至少被执行一次**。

#### 示例

```c
void foo(int a, int b) {
    int x = 0;
    if (a > 0 && b > 0) {   // 判定T1
        x = x + 1;           // 语句S2
    }
    printf("%d", x);         // 语句S3
}
```

测试用例：`a=1, b=1` → 执行路径 S1→S2→S3，所有语句都被执行。

#### 主要特点

- **覆盖强度最低**，是最基本的覆盖要求
- 只关心"语句是否被执行过"，**不关心分支的走向**
- 无法发现逻辑运算符错误（如 `&&` 写成 `||`）
- 无法发现条件判断中的遗漏分支
- 实现成本低，但**检错能力很弱**

---

### 2.2 判定覆盖（Decision Coverage / 分支覆盖）

#### 定义

设计足够多的测试用例，使得程序中**每个判定的"真"分支和"假"分支都至少执行一次**。

#### 示例

同上代码，需要两组用例：
- `a=1, b=1` → 判定为 **T**，走 S2
- `a=-1, b=1` → 判定为 **F**，跳过 S2

#### 主要特点

- 强度**高于语句覆盖**（分支覆盖必然覆盖所有语句）
- 关注的是**整个判定表达式的最终结果**（整体为真/为假），而非其中的每个条件
- 无法检测**条件内部的错误**：例如 `a > 0 && b > 0` 中若将 `b > 0` 误写为 `b < 0`，在 `a=1, b=1` 和 `a=-1, b=-1` 下仍可能满足分支覆盖，但逻辑已经错误
- 是实际工程中**最常用的最低覆盖标准**

---

### 2.3 条件覆盖（Condition Coverage）

#### 定义

设计足够多的测试用例，使得每个判定中**每个条件的各种可能取值（真/假）至少出现一次**。

#### 示例

判定 `if (a > 0 && b > 0)` 包含两个条件：
- 条件 C1：`a > 0`
- 条件 C2：`b > 0`

需要覆盖：
- `a=1, b=-1` → C1为T，C2为F
- `a=-1, b=1` → C1为F，C2为T

#### 主要特点

- 关注**单个条件**的取值，而非整个判定的结果
- **不保证分支覆盖**：上述两个用例可能都使整个判定为假，导致"真"分支从未执行
- 能发现条件内部的取值错误，但**可能遗漏分支走向的组合情况**
- 与判定覆盖互不包含（各有盲区）

---

### 2.4 判定/条件覆盖（Decision/Condition Coverage）

#### 定义

设计足够多的测试用例，使得：
1. 每个判定的**每个分支**（真/假）至少执行一次；**且**
2. 每个判定中**每个条件**的每种取值（真/假）至少出现一次。

#### 示例

同上代码，需要：
- `a=1, b=1` → 判定为T（覆盖真分支），C1=T，C2=T
- `a=-1, b=-1` → 判定为F（覆盖假分支），C1=F，C2=F

#### 主要特点

- 看似同时满足了判定覆盖和条件覆盖，但**存在致命盲区**
- **不能保证所有条件取值的组合都被覆盖**：上述用例中，C1=T & C2=F 和 C1=F & C2=T 这两种组合从未出现
- 当条件之间存在**冗余或短路求值**时，某些条件组合可能被掩盖
- 强度**高于判定覆盖和条件覆盖**，但**低于条件组合覆盖**

---

### 2.5 条件组合覆盖（Multiple Condition Coverage / Condition Combination Coverage）

#### 定义

设计足够多的测试用例，使得每个判定中**所有条件的各种可能取值组合**都至少执行一次。

#### 示例

判定 `if (a > 0 && b > 0)` 有两个条件，共 2² = 4 种组合：

| 用例 | C1: a>0 | C2: b>0 | 判定结果 |
|------|---------|---------|---------|
| a=1, b=1 | T | T | T |
| a=1, b=-1 | T | F | F |
| a=-1, b=1 | F | T | F |
| a=-1, b=-1 | F | F | F |

#### 主要特点

- **强度显著高于前四种**，能有效检测条件之间的交互错误
- 满足条件组合覆盖 **必然同时满足** 判定覆盖、条件覆盖、判定/条件覆盖
- 当条件数量多时，测试用例数**指数级增长**（n个条件需要2ⁿ个用例），代价很高
- 实际工程中常采用**基本路径测试**或**简化组合策略**来折中

---

### 2.6 路径覆盖（Path Coverage）

#### 定义

设计足够多的测试用例，使得程序中**所有可能的执行路径**都至少执行一次。

#### 示例

```c
void bar(int a, int b) {
    int x = 0;
    if (a > 0) {          // 判定D1
        x = x + 1;        // S2
    }
    if (b > 0) {          // 判定D2
        x = x + 2;        // S4
    }
    return x;
}
```

共4条路径：
1. D1=T → D2=T：S1→S2→S3→S4→S5
2. D1=T → D2=F：S1→S2→S3→S5
3. D1=F → D2=T：S1→S3→S4→S5
4. D1=F → D2=F：S1→S3→S5

#### 主要特点

- **覆盖强度最高**，能发现路径相关的错误（如初始化遗漏、变量未正确更新）
- 满足路径覆盖 **必然满足** 上述所有覆盖标准
- 当程序包含**循环**时，路径数量可能是**无限的**，无法完全实现
- 实际中通常采用**基路径测试（McCabe圈复杂度）**来选取线性独立路径的子集

## 三、覆盖标准强度对比总结

| 覆盖标准 | 关注对象 | 强度等级 | 能否保证分支覆盖 | 能否保证条件覆盖 | 主要盲区 |
|---------|---------|---------|----------------|----------------|---------|
| 语句覆盖 | 每条语句 | ★☆☆☆☆ | ✗ | ✗ | 分支走向、条件取值 |
| 判定覆盖 | 每个判定的整体结果 | ★★☆☆☆ | ✓ | ✗ | 条件内部取值错误 |
| 条件覆盖 | 每个条件的取值 | ★★☆☆☆ | ✗ | ✓ | 分支走向的组合 |
| 判定/条件覆盖 | 判定+条件（分别） | ★★★☆☆ | ✓ | ✓ | 条件取值组合 |
| 条件组合覆盖 | 条件取值的所有组合 | ★★★★☆ | ✓ | ✓ | 路径组合（循环路径） |
| 路径覆盖 | 每条执行路径 | ★★★★★ | ✓ | ✓ | 无（但循环时不可完全实现） |

---

## 四、工程实践中的选择建议

1. **最低要求**：至少达到**判定覆盖**，这是多数安全关键标准（如DO-178C Level D）的基线要求。
2. **推荐标准**：对于中等安全等级，通常要求**修正条件/判定覆盖（MC/DC）**——这是条件组合覆盖的一种实用简化形式，在航空电子等领域被强制要求。
3. **高安全等级**：要求**MC/DC + 路径覆盖的充分子集**，并结合圈复杂度控制代码复杂度。
4. **实际权衡**：覆盖标准越高，测试成本越大。工程中需要在**检错能力**与**测试成本**之间找到平衡点。

### 软考系统架构设计师案例分析模拟题（微服务架构方向）

**【试题一】阅读下列说明，回答问题1至问题3，将解答填入答题纸的对应栏内。**

**【说明】**
某大型连锁餐饮企业原有的门店管理系统采用单体架构，涵盖门店点菜、厨房出单、库存管理、会员服务、外卖平台对接等核心业务模块。随着企业门店数量突破5000家、日均订单量超过200万单，原有系统暴露出以下严重问题：
- 各业务模块耦合度高，新功能上线需全量部署，发布周期长达2周，且一次发布失败影响所有门店；
- 外卖高峰期（午市、晚市）订单量激增，系统无法针对热点模块独立扩容，多次出现服务不可用；
- 不同外卖平台（美团、饿了么、抖音）的接入逻辑混杂在核心代码中，新增平台对接需要修改大量代码；
- 各门店存在弱网环境，网络不稳定时点菜功能不可用，严重影响用户体验；
- 跨模块业务（如下单后扣减库存、更新会员积分）的数据一致性难以保证，经常出现库存扣减成功但订单创建失败的情况。

为解决上述问题，公司决定对门店管理系统进行微服务架构改造。作为系统架构师，你负责主导整体架构设计与核心方案选型，采用以下技术路线：
- 基于领域驱动设计（DDD）进行服务拆分，划分点菜、厨房、库存、会员、外卖网关等限界上下文；
- 采用 Spring Cloud Alibaba 技术栈（Nacos 注册中心、Gateway 网关、Sentinel 流量治理、Seata 分布式事务）；
- 引入 RocketMQ 实现事件驱动的异步通信；
- 设计"离线优先"的数据同步方案，支持门店弱网环境下的正常点菜；
- 构建基于 SkyWalking 的全链路可观测体系。

### 参考答案与解析

**【问题1】参考答案**

**1. 限界上下文的概念及指导意义（6分）**

**限界上下文**是 DDD 战略设计的核心概念，定义了特定领域模型的适用边界。在同一个限界上下文内，术语和模型具有明确且一致的含义。"限界"即"边界"，边界内是统一语言和统一模型。

**对微服务拆分的指导意义：**
- **提供拆分的理论依据**：一个限界上下文通常映射为一个微服务，确保服务边界与业务边界对齐；
- **明确服务间的数据边界**：不同上下文对同一概念可以有不同模型（如"订单"在点菜上下文关注菜品列表，在厨房上下文关注制作状态）；
- **指导 API 设计**：跨上下文通信通过定义明确的上下文映射（防腐层 ACL、开放主机服务 OHS 等）实现，避免模型污染。

**2. 限界上下文与微服务对应关系（6分）**

| 限界上下文 | 对应微服务 | 核心职责 |
|:---|:---|:---|
| **点菜上下文** | 点菜服务 | 处理顾客下单、订单状态流转、购物车管理 |
| **厨房上下文** | 厨房出单服务 | 接收订单、分配档口、管理菜品制作状态、出餐通知 |
| **库存上下文** | 库存服务 | 管理食材库存、扣减库存、库存预警与补货提醒 |
| **会员上下文** | 会员服务 | 会员注册/登录、积分管理、会员等级与权益 |
| **外卖上下文** | 外卖网关服务 | 对接美团/饿了么/抖音等第三方平台，统一订单格式转换与路由 |

> 答出任意4个即可得满分。

**【问题2】参考答案**

**1. "离线优先"架构的核心设计思想（3分）**

"离线优先"（Offline-First）的核心思想是：**将门店本地作为数据的第一可信源，网络仅作为数据同步的通道而非必要条件**。即使在网络中断的情况下，门店仍能正常完成点菜、下单等核心业务；网络恢复后，本地数据自动与云端同步，保证最终一致性。

**2. 核心流程设计（7分）**

**（1）门店本地数据一致性保证：**
- 门店端部署轻量级本地数据库（如 SQLite / LevelDB），存储菜单、会员基础信息等只读数据的本地副本；
- 点菜操作先在本地数据库写入订单记录，采用本地事务保证原子性；
- 为每条本地记录生成全局唯一 ID（如雪花算法），作为云端同步的去重标识。

**（2）网络恢复后的云端同步：**
- 网络连通后，门店端启动同步代理，将本地未同步的订单按时间顺序批量上传至云端；
- 云端接收后写入中心数据库，并通过 RocketMQ 发布"订单已创建"事件，触发库存扣减、积分更新等下游流程；
- 同步成功后，云端返回确认 ACK，门店端标记本地记录为"已同步"。

**（3）数据冲突处理：**
- **冲突场景**：同一订单在本地和云端都被修改（如订单状态变更）、库存数据不一致等；
- **处理策略**：
  - 采用**版本向量（Version Vector）**或**最后写入胜出（LWW）**策略解决简单冲突；
  - 对于业务关键冲突（如库存不足），由云端返回冲突信息，门店端提示用户手动处理或执行补偿操作（如取消订单、通知用户更换菜品）；
  - 建立**冲突日志**，供管理员事后审计和人工干预。

**【问题3】参考答案**

**1. 最终一致性与强一致性对比（4分）**

**最终一致性**是弱一致性的一种特殊形式，允许数据在短时间内存在不一致，但保证在没有新的更新操作后，系统最终会收敛到一致状态。

| 对比维度 | 强一致性 | 最终一致性 |
|:---|:---|:---|
| **数据可见性** | 写操作完成后，所有读操作立即读到最新值 | 写操作完成后，可能存在短暂的不一致窗口 |
| **可用性** | 低（需等待所有副本同步，节点故障时可能不可用） | 高（允许部分节点暂时不同步，服务持续可用） |
| **性能** | 低（同步阻塞，延迟高） | 高（异步处理，响应快） |
| **适用场景** | 金融转账等强一致性要求场景 | 电商下单、库存扣减等可容忍短暂不一致的场景 |

在微服务架构中，基于 CAP 理论，通常在保证分区容错性（P）的前提下，在一致性（C）和可用性（A）之间做权衡，多数业务场景选择 AP + 最终一致性。

**2. 基于 RocketMQ + 补偿机制的实现流程（4分）**

结合"下单→扣减库存"场景，核心流程如下：

1. **点菜服务**接收到下单请求后，在本地数据库创建订单（状态为"待确认"），并向 RocketMQ 发送一条**事务消息**（半消息），消息内容为"扣减库存"指令；
2. RocketMQ 持久化该消息但暂不对消费者可见，回调点菜服务的确认接口；
3. 点菜服务确认订单创建成功后，向 RocketMQ 提交 **Commit**，消息投递给**库存服务**；若订单创建失败，则发送 **Rollback**，消息被丢弃；
4. **库存服务**消费消息，执行本地库存扣减。扣减成功则返回 ACK；扣减失败（如库存不足）则发布"库存不足"事件；
5. **点菜服务**订阅"库存不足"事件，执行**补偿操作**：将订单状态更新为"已取消"，并通知用户；
6. 引入**分布式调度框架**（如 XXL-JOB）定期扫描超时未完成的订单，触发补偿或告警，确保所有事务最终收敛。

> 关键点：事务消息保证消息不丢失、不重复投递；补偿机制处理业务失败场景；幂等性设计防止消息重复消费导致数据错误。

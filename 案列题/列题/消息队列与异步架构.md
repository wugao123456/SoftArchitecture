### 软考系统架构设计师案例分析模拟题（消息队列与异步架构方向）

**【试题一】阅读下列说明，回答问题1至问题4，将解答填入答题纸的对应栏内。**

**【说明】**
某大型电商平台的核心交易系统原采用同步调用链实现订单履约流程。用户提交订单后，订单服务需依次同步调用优惠券服务、库存服务、支付服务、积分服务、风控服务、物流服务、短信通知服务等12个下游服务，整条链路平均响应时间为4.5秒，P99超过11秒。随着业务规模扩大（日均订单量达800万单，大促峰值QPS超3万），系统暴露出以下严重问题：

- **链路脆弱**：任意一个非核心下游服务（如短信通知、积分累加）超时或宕机，都会导致整个下单请求失败，大促期间故障率高达7%；
- **峰值雪崩**：促销开场瞬间流量洪峰直接穿透到所有下游服务，积分、物流等非核心系统率先被打垮，进而拖垮核心交易链路；
- **数据不一致**：订单创建成功但积分未累加、库存已扣减但优惠券未核销，每天需人工对账修复数千笔异常单；
- **消息重复**：引入消息队列解耦后，出现同一订单被发货两次、积分被重复累加的问题；
- **消息丢失**：极端情况下出现"用户付款成功但订单状态未更新"的漏单现象，引发大量客诉；
- **顺序错乱**：同一订单的"已付款→已发货→已签收"状态事件被乱序消费，导致用户收到错误的状态推送；
- **消费积压**：下游处理能力不足时，消息队列积压量一度达到千万级，延迟从秒级恶化到小时级。

架构团队决定采用**消息队列 + 异步化架构**进行改造，技术选型为 RocketMQ，并制定以下改造原则：核心交易链路只保留"创建订单 + 预扣库存 + 生成支付单"三个同步操作，其余全部异步化；通过可靠消息最终一致性保证数据一致；建立完善的消息治理体系（幂等、顺序、积压、死信）。

### 参考答案与解析

#### 【问题1】参考答案

**1. 异步化判定的三条准则（3分）**

| 准则 | 说明 |
|:---|:---|
| **是否影响主流程的正确性** | 若该操作失败会导致主业务结果错误（如扣库存失败却生成订单），则必须同步并在主事务内完成或采用分布式事务；若仅影响辅助体验，可异步 |
| **用户是否需要立即感知结果** | 用户需即时得到反馈的操作（如支付结果、库存是否充足）必须同步；用户无感知的后续动作（如发通知、记日志、算积分）可异步 |
| **下游的稳定性与性能是否可控** | 对稳定性差、响应慢、非本团队维护的第三方服务，应避免同步依赖，改为异步+补偿 |

> 补充准则（答出亦可得分）：操作是否具备**幂等性**（不可幂等的操作需谨慎异步）、是否存在**反向依赖**（后续步骤需要本次操作的返回值则不能异步）。

**2. 同步/异步划分（5分）**

| 操作 | 分类 | 理由 |
|:---|:---|:---|
| 创建订单主记录 | **必须同步** | 主流程核心，用户需立即获知订单是否成立，且是后续所有操作的源头 |
| 预扣库存 | **必须同步** | 防止超卖，失败则订单不能成立，属于主流程正确性的必要条件 |
| 生成支付单 | **必须同步** | 用户需立即跳转支付，且支付单号需返回给前端 |
| 累加会员积分 | **可以异步** | 不影响订单成立，用户无需即时感知，属辅助性操作 |
| 发送短信通知 | **可以异步** | 纯通知类操作，第三方服务稳定性差，同步会拖垮主链路 |
| 风控评分 | **可以异步**（或降级同步） | 若风控用于事后审计可异步；若用于拦截高风险订单则需同步但须设超时熔断兜底 |
| 推送物流单号 | **可以异步** | 发生在支付成功后，与下单主链路无强时序耦合 |

#### 【问题2】参考答案

**1. 本地消息表方案核心流程（6分）**

```
客户端        订单服务                 本地消息表              MQ              积分服务
  │             │                        │                    │                 │
  │──下单──────▶│                        │                    │                 │
  │             │──①开启本地事务────────│                    │                 │
  │             │──②写订单表────────────▶│                    │                 │
  │             │──③写消息表(status=待发送)▶│                    │                 │
  │             │──④提交本地事务────────│                    │                 │
  │             │                        │                    │                 │
  │             │──⑤发送消息 ──────────────────────────────▶│                 │
  │             │──⑥更新消息表(status=已发送)▶│                    │                 │
  │             │                        │                    │──投递────────▶│ ⑦消费并累加积分
  │             │                        │                    │◀──ACK ────────│
  │             │                        │                    │                 │
  │             │◀──⑧定时任务扫描"待发送"超时消息重发────────────────────────────│
```

**各步骤作用：**
- ①~④：**将"业务数据落库"与"消息记录落库"放在同一个本地数据库事务中**，利用单机 ACID 保证二者原子性——这是本方案的核心思想，彻底消除"业务成功但消息没记下来"的不一致；
- ⑤~⑥：事务提交后发送消息到 MQ，成功后将消息表状态置为"已发送"；
- ⑦：下游服务消费消息执行业务，成功后返回 ACK；
- ⑧：**定时补偿任务**扫描"待发送"超过阈值（如5分钟）的消息并重发，同时扫描"已发送"但下游未 ACK 的消息进行重试，保证消息至少投递一次。

**2. 两种异常的处理（4分）**

| 异常场景 | 处理方式 |
|:---|:---|
| **本地事务成功但消息发送失败** | 消息表中该记录状态仍为"待发送"，由定时补偿任务扫描并重发；也可在发送前先将消息写入消息表（status=待发送），事务提交后再发，确保消息一定存在 |
| **消息发送成功但本地事务回滚** | 业务数据已回滚，但消息已发出（孤儿消息）。下游消费时需做**前置校验**：收到消息后反查订单主表，若订单不存在或状态不合法，则判定为无效消息，丢弃或进入死信队列等待人工处理。**这是本方案的关键考点，答出"下游反查校验"才完整** |

> 替代方案（答出亦可）：使用 RocketMQ **事务消息（Half Message）**机制，利用回调检查本地事务状态来决定 Commit/Rollback，原理相同但由 MQ 侧驱动补偿。

#### 【问题3】参考答案

**1. 重复消息原因与幂等方案（4分）**

**产生重复的三个原因：**
1. **生产者重发**：网络抖动导致发送超时，生产者未收到响应而重试，MQ 实际已落盘；
2. **MQ 侧重投**：Broker 主从切换、消息刷盘重试等内部机制导致重复投递；
3. **消费者 ACK 丢失**：消费者已处理成功但 ACK 报文丢失，Broker 超时后重新投递。

**幂等性方案（推荐组合）：**
- **唯一幂等键 + 去重表**：以业务天然唯一标识（如订单号 + 操作类型）作为幂等键，消费前先查询去重表（Redis `SETNX` 或数据库唯一索引表），不存在则插入并执行业务，存在则直接返回成功；
- **状态机幂等**：对订单等状态流转型业务，用 `UPDATE ... SET status='已发货' WHERE id=? AND status='已付款'` 的条件更新，利用受影响行数判断是否真正执行，天然防重；
- **乐观锁版本号**：记录携带 version，更新时校验 version 并 +1，版本不匹配则拒绝；
- **下游防重校验**：在支付、发货等资金/实物环节增加二次校验（如查询是否已存在对应流水）。

> 关键点：去重表的插入与业务执行必须在**同一本地事务**内，否则仍会出现"插入了去重记录但业务失败"的不一致。

**2. 顺序消息方案与局限性（4分）**

**设计方案：**
- **分区（队列）级别有序**：RocketMQ 保证同一 MessageQueue 内的消息 FIFO。将**同一订单的所有事件按订单ID哈希路由到同一个 Queue**（`MessageQueueSelector` 按 orderId 选择），即可保证该订单的状态事件严格按发送顺序消费；
- **单线程顺序消费**：消费者侧对该 Queue 使用单线程串行消费（`ConsumeOrderly` 模式），避免并发打乱顺序；
- **失败阻塞重试**：顺序消费模式下某条消息处理失败会阻塞后续消息，需设置合理的重试次数与死信队列，防止单条坏消息卡死整个队列。

**局限性：**
1. **牺牲并发度**：同一 Queue 只能单线程消费，热点订单（如大促销品）会成为瓶颈，吞吐量大幅下降；
2. **全局有序不可行**：跨 Queue 无法保证顺序，若业务要求全局有序则只能单 Queue 单消费者，完全失去扩展性；
3. **失败扩散风险**：一条消息持续失败会导致同队列所有订单的事件堆积，必须配合死信队列与人工干预机制；
4. **扩容重平衡会短暂乱序**：消费者组扩缩容触发 Rebalance 时，Queue 重新分配期间可能出现短暂乱序。

#### 【问题4】参考答案

**1. 千万级积压紧急处置（5分，按优先级）**

| 优先级 | 措施 | 说明 |
|:---|:---|:---|
| **P0** | **临时扩容消费者 + 队列再分发** | 新建一个 Topic，配置 10 倍于原数量的 Queue；部署一批只做"转发"的临时消费者，把积压消息按 key 哈希均匀转发到新 Topic 的多个 Queue，再由大量新消费者并行处理。这是解决"Queue 数量不足限制消费并发"的标准做法 |
| **P0** | **暂停非核心生产者** | 关闭积分、通知、推荐等非核心链路的消息发送，防止积压继续恶化，优先保障交易、支付等核心消息 |
| **P1** | **消费者逻辑降级为批量写** | 将逐条处理改为批量拉取 + 批量入库，减少 DB 交互次数；跳过非必要的校验与外部调用 |
| **P1** | **业务降级与丢弃** | 对时效性强的消息（如状态推送、实时报表）设定 TTL，过期直接丢弃或仅保留最新一条（合并同类消息） |
| **P2** | **提升消费者资源与并行度** | 增加消费者实例 CPU/内存，调大拉取批次（pullBatchSize）与并发线程数，但不得超过 Queue 数量 |
| **P2** | **死信与异常隔离** | 连续失败 N 次的消息转入死信队列，避免反复重试占用消费能力；单独起任务事后补跑 |

> 补充：事后必须进行**根因复盘**——是消费逻辑慢、DB 成为瓶颈，还是生产者速率失控，否则下次大促仍会重现。

**2. 背压机制原理与实施（4分）**

**原理：** 背压是一种**由消费者主导的流量控制机制**。传统推模式下生产者不管下游处理能力盲目发送，容易导致消费者过载甚至崩溃；背压则让消费者根据自身剩余处理能力（credit/permit）向上游反馈"还能接收多少"，生产者在额度耗尽时暂停发送或缓冲，从而将压力反向传导至源头，使系统整体稳定在消费者的实际吞吐能力之内。

**本案例中的实施：**

| 位置 | 实施方式 |
|:---|:---|
| **消费者侧（主动反馈）** | 采用**拉取（Pull）模式**代替 Push，消费者按自身吞吐能力控制 `pull` 的频率与批次大小；设置消费端限流（如每秒最多处理 N 条），超额则暂停拉取；利用 RocketMQ 的流控参数（`pullThresholdForQueue`、`consumeConcurrentlyMaxSpan`）限制内存中堆积的未确认消息数 |
| **生产者侧（被动降速）** | 接收到背压信号后，先在本机缓冲区暂存或减速发送；缓冲区满则触发**降级策略**：非核心消息直接丢弃（如通知类）、核心消息走本地磁盘持久化队列待后续补发；同时向上游返回友好提示（如"下单排队中"），避免用户重复提交 |
| **系统级兜底** | 在入口层（网关/Sentinel）实施**限流与削峰**，从源头控制进入系统的请求速率，这是最根本的背压——把压力挡在系统之外而非压在队列里 |

### 备考提示

本题覆盖了消息队列与异步架构方向的高频考点，建议重点掌握：

| 考点 | 考查频率 | 记忆要点 |
|:---|:---|:---|
| 同步/异步边界划分 | ★★★★★ | 正确性、即时感知、下游可控三准则 |
| 可靠消息最终一致性 | ★★★★★ | 本地消息表 / 事务消息 / 定时补偿 / 下游反查 |
| 幂等性设计 | ★★★★★ | 唯一键+去重表、状态机、乐观锁、同一事务 |
| 顺序消息 | ★★★★ | 分区有序、key 哈希路由、单线程消费、牺牲并发 |
| 消息积压处置 | ★★★★ | 扩容 Queue + 转发 Topic、降级、批量、死信 |
| 背压与削峰 | ★★★ | Pull 模式、credit 反馈、入口限流 |
| 消息丢失与重复 | ★★★★ | 三段确认（生产/Broker/消费）、ACK 机制 |
| 异步架构的风险 | ★★★ | 可观测性下降、调试困难、事务边界模糊、最终一致性带来的用户体验折损 |

**答题提醒**：案例题中出现"引入消息队列后出现了XX问题"，标准答题结构永远是**"原因分析 → 机制设计 → 兜底方案"**三层。只写"加个幂等"拿一半分，写出"幂等键如何定义、放在哪个事务、冲突后怎么处理"才能拿满分。

**【说明】**
某全国性即时零售平台（覆盖 300 城、日均订单 1200 万单、峰值下单 QPS 3.5 万）的数据库架构面临全面重构。现状如下：

- **单库单表已到极限**：核心 `orders` 表已达 9.6 亿行、420GB，`order_items` 表 38 亿行；最大分区（按 `create_time` 月分区）单表超 8000 万行，DDL 变更平均耗时 6~14 小时，期间主从延迟飙升至分钟级；
- **混合负载互相干扰**：同一套 MySQL 集群既承载下单/支付等 OLTP 请求，又承载运营即席查询、商家报表与风控模型取数，夜间批量任务常把 CPU 打满，导致早高峰下单超时；

- **时效与一致性要求分层**：下单扣库存、支付必须强一致；订单状态流转允许秒级延迟；报表与分析可接受 T+0 小时级或 T+1，但要求口径准确、可回溯；
- **合规与留存**：交易明细在线保留 3 年，冷数据归档保留 10 年；需支持监管按需调阅任意历史订单，且不得影响在线库性能；
- **历史教训**：一期曾采用"读写分离 + 大表按月分区"缓解，但出现：①主从延迟导致用户刚下单却查不到订单（投诉率高）；②从库被分析查询拖垮后反向影响主库复制；③部分查询未带分区键导致全分区扫描；④一次主库故障切换后出现少量重复订单号。

### 参考答案与解析

#### 【问题1】参考答案

**1. 三种路线对比（5分）**

| 对比维度 | 垂直拆分 / 读写分离 | 水平分库分表（Sharding） | 原生分布式数据库（TiDB/OceanBase） |
|:---|:---|:---|:---|
| **扩展方式** | 垂直按业务拆库；写仍为单点，读通过加从库横向扩展 | 按分片键哈希/范围拆分，写能力随分片数线性提升 | 计算存储分离，自动 Range 分片（Region/Tablet），对应用透明 |
| **一致性** | 主从异步复制，**存在延迟**；读写分离需处理弱一致 | 分片内强一致；跨分片依赖分布式事务或最终一致 | 内置 Raft/Paxos 多副本强一致，跨节点事务由引擎保证 |
| **负载隔离** | 差——从库同时承载报表会拖垮复制，案例已发生 | 中——OLTP 与 OLAP 仍需物理隔离 | 好——HTAP 引擎提供行列共存的分析副本，天然隔离 |
| **运维复杂度** | 低（成熟、团队熟悉） | **高**——需中间件（ShardingSphere/Mycat）、跨分片查询/聚合/排序/全局索引均需手工处理、扩容需 rebalance | 中——组件多（PD/TiKV/TiFlash），但免去了分片规则设计与扩容重分布的手工工作 |
| **成本** | 低 | 中（机器数增加，但可用普通 MySQL） | 较高（需 SSD、内存充裕；TiFlash 列存副本额外占用存储） |
| **适用** | 写少读多、业务边界清晰、数据量未破单机上限 | 写吞吐是瓶颈、分片键明确、团队有中间件能力 | 写读双高、希望免运维分片、需要一份数据同时做 TP+AP |
| **短板** | 写瓶颈无法解决；从库越多延迟越大 | 跨分片 join/聚合困难；分布式事务性能差；扩容痛苦 | 单点长事务与大范围扫描会拖垮集群；生态兼容细节差异；硬件成本高 |

**2. 选型结论与分层方案（4分）**

**结论：不选单一路线，采用"分库分表承载 OLTP + HTAP 分析副本承载 AP + 对象存储归档承载冷数据"的分层架构。**

| 层级 | 技术 | 承载负载 | 说明 |
|:---|:---|:---|:---|
| **在线 OLTP 层** | MySQL 8.0 **分库分表**（16库×64表，按 `member_id` 哈希） | 下单、支付、查询我的订单等高频点查与小事务 | 写能力线性扩展；分片内事务走本地，性能最优 |
| **实时同步层** | Canal/DM/CDC → Kafka | 将 binlog 实时分发到下游 | 解耦上下游，削峰，作为数据总线 |
| **HTAP 分析层** | TiDB + **TiFlash 列存副本**（或 Doris/StarRocks） | 运营即席查询、商家报表、风控特征宽表 | 与在线库物理隔离，消除"报表拖垮主库"；准实时（秒~分钟级） |
| **检索层** | Elasticsearch | 客服按订单号/手机号/运单号任意字段反查 | 倒排索引解决"非分片键反查"与模糊匹配 |
| **冷数据归档层** | 对象存储 + Parquet/Iceberg（或定期导出到数仓 ODS） | 3年以上历史明细，满足 10 年合规留存 | 成本极低；监管调阅走离线查询，不影响在线库 |
| **缓存层** | Redis | 热点订单详情、用户最近订单入口 | 抗 QPS，降低 DB 点查压力 |

**为什么不直接全部迁到分布式数据库：**
1. **成本与硬件约束**：分布式数据库通常要求全闪存与较大内存，本案例存量数据数百 TB 级，一次性迁移成本远超预算；
2. **迁移风险过大**：9.6 亿行核心表的一次性割接风险不可控，且团队对分布式数据库的调优经验不足（SQL 改写习惯、执行计划差异、长事务陷阱）；
3. **混合负载本质应靠"隔离"而非"统一引擎"解决**：即使上了 HTAP，OLTP 与重度 OLAP 共用同一集群仍存在资源争抢风险，物理隔离更稳妥；
4. **分库分表在"分片键明确 + 事务局限在分片内"的场景下性能更可控**，且现有代码改造量可通过中间件透明化；
5. **演进式优于革命式**：先分库分表解写瓶颈、CDC 建分析副本解读瓶颈，未来若确实需要可再平滑过渡到分布式库（CDC 链路复用）。

#### 【问题2】参考答案

**1. 分片键选择（4分）**

**推荐分片键：`member_id`（用户ID）哈希分片。**

**依据：**
- **高频访问局部性**：C 端"我的订单"是最高频查询（QPS 2 万+），按 `member_id` 分片可使该查询**路由到单一分片**，避免广播；
- **事务局部性**：下单、支付、查订单大多发生在"用户"维度内，分片内即可完成本地事务，避免分布式事务；
- **写均匀性**：用户 ID 分布相对均匀，不易产生热点（相比按 `city_id` 会产生大城市热点，按时间会产生新分区热点）。

**四类查询命中情况：**

| 查询场景 | 是否命中分片 | 说明 |
|:---|:---|:---|
| 用户查我的订单 | ✅ 命中单分片 | 携带 `member_id`，直接路由，性能最优 |
| 商家查本店订单 | ❌ 需广播或走异构索引 | 商家维度与用户维度正交，需全分片扫描（可用**基因法**或 ES 旁路解决） |
| 客服按订单号查 | ❌ 需广播 | 订单号不含分片信息 → 用**基因法**（订单号低位嵌入 `member_id` 哈希值）可转为单分片路由 |
| 运营按城市统计 | ❌ 全分片聚合 | 这是 OLAP 负载，**不应走在线分库**，应下沉到 HTAP 分析层 |

> **关键取舍表达**：分片键只能有一个主维度，其余维度的查询必须靠**冗余/异构索引/旁路检索**补齐，这正是分库分表的固有代价。

**2. 全局唯一 ID（3分）**

| 方案 | 优点 | 缺点 | 本案例评价 |
|:---|:---|:---|:---|
| **数据库号段/序列**（如单独 DB 自增步长、Leaf-segment） | 绝对有序、单调递增、实现简单 | 单点瓶颈（虽可用号段缓冲缓解）、DB 故障影响发号 | 适合对有序性要求强的场景；本案例可作为备用 |
| **雪花算法（Snowflake）** | 本地生成、无网络开销、高性能、趋势递增 | 依赖时钟（回拨产生重复ID）、需分配唯一 workerId、时钟同步 | **本案例推荐**（下单 QPS 3.5 万，发号不能成为瓶颈） |
| **UUID** | 全局唯一、无协调 | 无序导致 B+树页分裂与随机 IO、过长占存储、不可读 | ❌ 不推荐作主键（但可作业务流水号辅助） |

**雪花算法风险与对策：**
- **时钟回拨**：系统时钟回调会导致 ID 重复。对策：①记录上次生成时间，检测到回拨则拒绝发号并告警（等待追平）；②引入**时钟回拨容忍窗口**（如 <10ms 则自旋等待）；③使用增强版（如美团 Leaf、百度 UidGenerator 的 clock backward 处理）；④部署 NTP 平滑同步（禁用大步长跳变）。
- **workerId 分配**：多实例部署时 workerId 冲突会导致重复 ID。对策：①基于 ZooKeeper/etcd 动态分配并持久化到本地文件；②将 workerId 与容器实例 ID/IP 绑定，启动时注册；③采用**号段+雪花混合**（号段服务分配 segment，实例内自增），彻底摆脱机器 ID 依赖——**这是生产环境更稳妥的做法**。

**3. 跨分片查询四种手段（3分）**

| 手段 | 原理 | 本案例适用场景 |
|:---|:---|:---|
| **基因法（冗余分片键）** | 在订单号等 ID 的低几位嵌入 `member_id` 的哈希值（基因位），解析 ID 即可反推目标分片 | 客服/网关仅凭**订单号**即可路由到单分片，避免广播；外卖订单号、快递单号常用此法 |
| **异构索引表（映射表）** | 建立 `idx_order_no → member_id`、`idx_shop_order → (shop_id, order_id)` 等小映射表，按查询维度分片，先查映射得路由键，再查主表 | **商家查本店订单**、按运单号查订单；代价是写入需双写（同事务或异步+对账） |
| **ES/ClickHouse 旁路检索** | 通过 CDC 将全量数据同步到检索/分析引擎，非分片键查询走旁路，拿到 ID 列表后再回分库精确查询（或直接返回结果） | **客服任意字段反查**（ES）、**运营多维统计**（ClickHouse/Doris）——这也是负载隔离的手段 |
| **ER 分片（绑定表）** | 主子表按相同分片键与相同分片数拆分，使同一用户的订单与订单项落在同一分片，join 可在分片内完成 | `orders` 与 `order_items` 绑定，避免跨分片 join |

#### 【问题3】参考答案

**1. MVCC、隔离级别与主从延迟（5分）**

**MVCC 原理：** InnoDB 每行记录包含隐藏列 `DB_TRX_ID`（最近修改的事务ID）与 `DB_ROLL_PTR`（回滚指针），指向 undo log 中的历史版本链。事务开启时生成 **Read View**（包含当前活跃事务ID集合），读取时沿版本链找到**对本事务可见**的最新版本。这使得**读不加锁、读写不互斥**。

**四种隔离级别：**

| 级别 | 现象 | InnoDB 实现 |
|:---|:---|:---|
| **RU**（读未提交） | 脏读、不可重复读、幻读 | 直接读最新版本，不看 Read View |
| **RC**（读已提交） | 不可重复读、幻读 | **每次 SELECT 生成新 Read View**，只能见到已提交事务 |
| **RR**（可重复读，默认） | 理论上幻读 | **事务内首次 SELECT 生成 Read View 并复用**，故同一事务内多次读结果一致（解决不可重复读）；配合**间隙锁（Gap Lock）/ Next-Key Lock** 抑制幻读 |
| **Serializable** | 无 | 读也加锁，串行化，性能差 |

**RR 下"不可重复读已解决、幻读仍存在"的原因：**
- 不可重复读靠**Read View 复用**解决（同一事务看到同一快照）；
- 但**当前读**（`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE`）走最新数据，若其他事务在间隙插入新行，当前读仍会读到，形成幻读。InnoDB 用**间隙锁 + Next-Key Lock**（记录锁+前开闭区间间隙）锁住索引区间，阻止插入，从而在**大部分场景**下避免幻读；但若查询**未命中索引而退化为表锁/全表扫描**，或等值查询命中唯一索引，间隙锁退化，幻读仍可能发生。

**"主从延迟导致查不到刚下的订单"的问题定性与根治：**

| 层次 | 说明 |
|:---|:---|
| **定性** | 这不是隔离级别问题，而是**读写分离带来的最终一致性（会话级读己之写违反）**问题——写落在主库，读落到尚未同步的从库 |
| **治标** | ①写后强制读主（N 秒内或本次会话内路由到主库）；②关键链路（下单后立即跳转订单详情页）**强制走主库**；③前端做"乐观展示"（下单页直接渲染成功态，不依赖立即查询） |
| **治本** | ①**缩短复制延迟**：并行复制（MTS）、半同步复制、降低从库负载（把分析查询迁出从库——本案例根本病因）；②**架构上消除对从库的强依赖**：高频点查走 Redis 缓存（写时双写或订阅 binlog 更新），从库只承担非关键查询；③监控主从延迟秒数，超阈值自动切主读并告警 |

**2. 不停机双写迁移方案（4分）**

**六个阶段：**

```
阶段① 评估与设计：确定分片规则、全局ID方案、新旧表映射；新库预建 schema（含索引、字符集一致）
阶段② 全量数据迁移：离线工具（DataX/DM/mydumper）按主键分批拉取写入新库，限速错峰，不停写
阶段③ 增量追平：启动 CDC（canal/DM）订阅旧库 binlog，按顺序回放至新库，持续追赶直至延迟 < 1s
阶段④ 双向校验（最关键）：
       - 数量校验：按分片/天统计行数比对
       - 内容校验：抽样关键字段 hash 比对（金额、状态、时间），全量异步逐批校验
       - 业务校验：灰度流量双读比对结果集，差异超阈值告警并阻断
       - 建立"差异修复"闭环：发现差异→定位根因（丢binlog/乱序/类型转换）→补数据
阶段⑤ 灰度切流（双写期）：
       - 先"双写新旧"（以旧为主），验证无异常
       - 再按 userId 尾号/城市/商户 灰度读新库（1%→10%→50%→100%）
       - 切写：先切只读业务，再切写业务；切写瞬间需保证**新旧不再双向同步**（防环）
       - 观察指标：错误率、RT、数据差异率、主从延迟
阶段⑥ 收尾：旧库置为只读保留观察期（≥一个大促周期），确认无误后下线；保留回滚通道
```

**三个典型风险与应对：**

| 风险 | 应对 |
|:---|:---|
| **双写不一致/循环同步** | 单向同步为主；确需双向时用**标记位区分来源**（binlog event 打标），防止回环；以一方为权威源 |
| **全局ID冲突**（新旧两套发号器） | 迁移期新库 ID 高位设标识位/使用独立 workerId 区间，确保全域唯一且可区分来源 |
| **DDL/结构变更不同步** | 迁移冻结期禁止 schema 变更；或借助 gh-ost/pt-online-schema-change 双端同步执行 |
| **切换瞬间流量冲击新库** | 提前预热缓存、连接池与索引；分批放量；准备**一键回滚开关**（配置中心下发，秒级切回旧库读） |
| **历史脏数据导致新库约束冲突** | 迁移前做数据质量清洗（空值、重复、外键悬空），冲突数据进隔离表人工处理 |

#### 【问题4】参考答案

**1. 慢 SQL 定位与优化（4分）**

**定位：**
- 通过慢查询日志（`long_query_time`）、`performance_schema`、PMM/PMDB 大盘定位 Top SQL；
- `EXPLAIN` 关键关注项：`type`（是否 ALL/index/range/ref）、`possible_keys`/`key`（是否命中预期索引）、`rows`/`filtered`（扫描行数）、`Extra`（**Using filesort**、**Using temporary**、Using index condition、Backward index scan）。

**该 SQL 的问题：**
1. `ORDER BY create_time DESC LIMIT 1000, 20` 是**深分页**：需扫描并排序前 1020 行再丢弃，越往后越慢；且 `create_time` 非索引前列时需 filesort；
2. `SELECT *` 无法走**覆盖索引**，需大量**回表**（二级索引取到主键再聚簇索引查整行）；
3. 复合索引缺失或顺序不当：`status IN (...)` 为范围条件，应放在等值条件 `member_id` 之后。

**优化手段：**
| 手段 | 具体做法 |
|:---|:---|
| **建合适复合索引** | `idx_member_status_time(member_id, status, create_time)` —— 等值在前、范围在后、排序键在末，可利用索引有序性避免 filesort；注意 `IN` 为多值时后续列有序性部分失效，需实测 |
| **覆盖索引减少回表** | 若只需少数字段，建 `idx_member_time(member_id, create_time)` 并在索引中包含所需列，避免 `SELECT *` |
| **深分页改造** | 改为**游标/seek 分页**：`WHERE member_id=? AND create_time < #{lastTime} ORDER BY create_time DESC LIMIT 20`（O(1) 复杂度）；或 `search_after` 思想；前端限制最大翻页数 + 提示细化条件 |
| **延迟关联（Late Row Lookups）** | 子查询先用覆盖索引拿到主键 ID，再 join 原表取整行：`SELECT * FROM orders o JOIN (SELECT id FROM orders WHERE ... LIMIT 1000,20) t ON o.id=t.id` |
| **冷热分离** | 历史订单归档，缩小单表扫描范围；加 `create_time` 范围过滤配合分区裁剪 |
| **其他** | 避免 `OR`/函数包裹列/隐式类型转换（导致索引失效）；控制 `IN` 列表长度；用 `UNION ALL` 替代复杂 OR |

**2. 高可用容灾与重复订单号（3分）**

**高可用方案：**
- **架构**：一主两从（跨可用区），**半同步复制（rpl_semi_sync）**保证至少一个从库收到 binlog 才提交，RPO ≈ 0（降级为异步时有监控告警）；
- **故障检测与切换**：Orchestrator/MHA/MGR 组复制，结合 VIP 或 DNS/Proxy（ProxySQL/HAProxy）漂移，**自动 failover + 手动确认**双模式（防脑裂需多数派可达、仲裁机制）；
- **RPO/RTO 目标**：同城双活 RPO≈0、RTO<30s；异地灾备采用异步复制 + 定期演练，RPO 分钟级、RTO 分钟~小时级；
- **备份**：全量（xtrabackup 每周）+ binlog 连续备份（保留 ≥10 年合规要求的归档策略），**定期恢复演练**（未演练的备份等于没有备份）；
- **连接层保护**：连接池（HikariCP）+ 超时与重试（幂等前提）+ 熔断，防 DB 抖动拖垮应用。

**"切换后出现重复订单号"的成因与防范：**

| 成因 | 防范 |
|:---|:---|
| **发号器状态未同步**：旧主库的发号器（如号段表/自增列）已消耗的值未同步到新主，新主重新发号产生冲突 | 发号器**独立于 DB**（Redis/ZK/号段服务）且自身高可用；或用雪花算法（本地发号，不依赖 DB）；切换后校验并**抬升号段上限** |
| **应用重试 + 非幂等**：切换瞬间超时，客户端重试生成新订单号但旧请求实际已成功（**最可能的主因**） | 订单创建接口**幂等化**：以 `client_token`/`request_id` 做去重表（与订单同库同事务），或业务唯一键唯一索引；重试先查再建 |
| **binlog 回放重复**：切换后从库晋升，部分已应用的 relay log 被重复执行 | 使用 GTID 复制，保证事务全局唯一、幂等回放；从库 `read_only=ON` 防双写 |
| **缓存/序列 cache 丢失**：MySQL `auto_increment` 缓存（innodb_autoinc_lock_mode）或 sequence cache 在宕机时跳号/回退 | 理解跳号属正常（不保证连续），但**绝不允许回退重复**；选用不回退的发号方案 |

### 📚 考点深度讲解

#### 一、这道题在考什么

数据库方向的核心不是背参数，而是考察**"数据怎么放、怎么访问、怎么不断、怎么不错"**四个决策：

| 层次 | 对应问题 | 考查本质 | 权重 |
|:---|:---|:---|:---|
| **架构选型** | 问题1 | 能否根据负载特征做分层，而非迷信"一个引擎通吃" | 约 25% |
| **数据分布设计** | 问题2 | 分片键 = 一切性能的源头，能否说清代价与补齐手段 | 约 28% |
| **一致性与演进** | 问题3 | MVCC 原理 + 不停机迁移（架构师的组织能力体现） | 约 25% |
| **治理与可用性** | 问题4 | 索引思维 + 容灾 RPO/RTO + 幂等兜底 | 约 22% |

#### 二、八大核心考点拆解

**考点1：读写分离的局限性（高频陷阱）**
读写分离**只解决读扩展，不解决写扩展与一致性**。答题必写三点代价：主从延迟（读己之写违反）、从库负载反噬主库复制、写热点无法缓解。本案例正是"从库被分析查询拖垮"的典型反面教材。

**考点2：分片键是唯一不可逆决策（最重要）**
分片键选定后几乎无法更改（需全量 rebalance）。选择三原则：**高频查询能路由、事务能局限在分片内、写入分布均匀**。并且必须主动承认"其他维度查询怎么办"——答不出这点会被认为没有实战经验。

**考点3：全局ID与雪花算法（必背细节）**
要能说出：有序性对 B+树写入友好的意义、时钟回拨处理、workerId 分配、号段模式原理。**"UUID 不适合做聚簇索引主键"**是经典得分句（随机IO、页分裂、存储膨胀、无趋势递增）。

**考点4：跨分片查询四件套**
基因法、异构索引表、旁路检索（ES/CH）、ER 分片。建议按"查询维度"归类作答，并写明每种方案的**写入代价**（双写/异步+对账）。

**考点5：MVCC 与隔离级别（原理级，区分度最高）**
必须说清：undo log 版本链 + Read View + 隐藏列；RC 每次语句新视图、RR 事务内复用视图；间隙锁/Next-Key Lock 的作用与退化条件。**"RR 也不能完全杜绝幻读"**这一表述是加分点。

**考点6：不停机数据迁移（架构师标志性题）**
六步法：设计→全量→增量→**校验**→灰度→收尾。其中**校验与回滚**是采分重心。阅卷看的是"你有没有想过失败怎么办"。记住口诀：**双写不双主、切流可回滚、差异可修复**。

**考点7：索引设计与深分页（实操必考）**
- 最左前缀、等值优先范围在后、覆盖索引减少回表、避免 `SELECT *`、警惕隐式类型转换与函数包裹；
- 深分页三种改法：**游标 seek 法（最优）**、延迟关联、限制最大页数；
- `EXPLAIN` 的 type 枚举顺序（system > const > eq_ref > ref > range > index > ALL）建议背下来。

**考点8：高可用与 RPO/RTO**
- 半同步复制 = 一致性与延迟的折中（Ack 等待，可设超时降级异步）；
- MGR/Galera 是基于 Paxos/Raft 的组复制，自动选主、防脑裂；
- **RPO 看数据丢多少，RTO 看停机多久**，两者往往互斥，答题时要给出具体数值目标；
- **备份必须演练恢复**——这句话写上去就是印象分。

#### 三、易混概念对照表

| 易混对 | 区分要点 |
|:---|:---|
| **脏读 / 不可重复读 / 幻读** | 脏读=读到未提交；不可重复读=同一行两次读值不同（更新）；幻读=两次读**行数**不同（插入/删除） |
| **当前读 vs 快照读** | 快照读（普通 SELECT）走 MVCC 历史版本；当前读（FOR UPDATE/UPDATE）读最新且加锁 |
| **半同步 vs 全同步 vs 异步** | 异步=主库不等从库（可能丢）；半同步=至少一个从库 ack（折中）；全同步=所有从库 ack（慢） |
| **分库分表 vs 分布式数据库** | 前者是分片规则在应用/中间件层，后者是引擎内置；前者灵活可控，后者免运维但黑盒 |
| **基因法 vs 异构索引表** | 基因法=把路由信息塞进 ID（零额外存储，但只能补一个维度）；异构索引表=独立映射表（可补多维度，但要双写） |
| **RPO vs RTO** | RPO=恢复点目标（丢多少数据）；RTO=恢复时间目标（停多久） |
| **深分页 vs 大表 DDL** | 前者改写法（游标）；后者用 pt-osc/gh-ost 在线变更或影子表切换 |
| **主从延迟 vs 隔离级别** | 主从延迟是**复制拓扑**问题，与事务隔离级别无关——本题最容易答偏的地方 |

#### 四、硬知识速记

| 项 | 要点 |
|:---|:---|
| EXPLAIN type 优劣序 | system > const > eq_ref > ref > range > index > **ALL（全表扫描，必优）** |
| Extra 危险信号 | Using filesort、Using temporary、Select tables optimized away |
| 索引失效常见原因 | 左模糊 `LIKE 'xx%'`✅ / `'%xx'`❌、列上函数/运算、隐式类型转换、OR 两侧不全有索引、联合索引违反最左前缀 |
| 深分页改造 | 游标 seek > 延迟关联 > 限制页数 |
| 分片数经验值 | 单表建议 ≤500万~1000万行 / ≤2GB；单库连接数 = 应用实例数×池大小，需预留 |
| 雪花算法 64bit | 符号位(1) + 时间戳(41) + 机器ID(10) + 序列(12)，约 69 年、每毫秒 4096 个 |
| 半同步复制 | `rpl_semi_sync_master_timeout` 超时降级异步，需监控降级次数 |
| binlog 格式 | ROW 格式最安全（含完整行镜像），用于 CDC/主从；STATEMENT 可能不一致 |
| 冷热分离 | 热（在线库，3个月）→温（历史库，1年）→冷（对象存储/数仓，3~10年） |
| CDC 作用 | 解耦 + 准实时同步 + 审计溯源，是湖仓/HTAP/ES 的数据总线 |

#### 五、答题通用骨架（数据库版）

```
① 负载画像：读/写比、QPS、数据量增长、时效分级、一致性分级
② 分层选型：OLTP 层 / 同步层 / 分析层 / 检索层 / 归档层（一层一引擎，不混跑）
③ 分布设计：分片键 → 全局ID → 跨分片补齐 → 事务边界
④ 一致性保障：隔离级别、复制拓扑、幂等、对账、兜底读主
⑤ 治理与演进：索引/SQL审核、容量预警、不停机迁移六步、RPO/RTO 与演练
```

#### 六、容易踩的坑

1. **把"主从延迟"归因于隔离级别**——这是本题最大的失分陷阱，两者毫无关系；
2. **只讲分库分表不讲代价**——跨分片查询、分布式事务、扩容、全局索引必须配套说明；
3. **迁移方案缺少校验和回滚**——写"半夜停机割接"基本不得分，现在考的都是不停机；
4. **用分布式锁/ES 解决所有查询**——要先判断"这个查询是否应该走在线库"，很多分析查询的正确解法是**换地方算**而不是**加索引**；
5. **忽略幂等**——重复订单号的根因往往是"超时重试 + 非幂等"，而非数据库本身；
6. **不提成本与人力**——架构师答案必须包含预算、团队能力、演进节奏的权衡。

#### 七、延伸考点清单（可能换皮出现）

| 考点 | 一句话要点 |
|:---|:---|
| SQL 审核与治理 | 上线前 explain 卡点、禁止 `SELECT *`/大事务/无 where 更新、慢 SQL 周报、索引生命周期（无用索引下线） |

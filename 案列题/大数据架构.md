**1. 三种架构对比（6分）**

| 对比维度      | Lambda 架构                                       | Kappa 架构                | 湖仓一体（批流一体）                     |

| **核心思想**  | 速度层（实时）+ 批量层（离线）双链路并行，结果合并                      | 只保留速度层，历史重算也通过流式回放完成    | 统一存储底座 + 统一表格式，一套代码同时服务批与流     |

| **运维成本**  | **最高**（两套集群、双倍人力，与本案例"8人团队"直接冲突）                | 中（重放资源消耗大）              | 较低（存算分离、统一元数据、一份数据多引擎访问）       |
| **典型短板**  | 维护成本高、逻辑冗余                                      | 状态回溯成本高、流引擎压力大、不适合复杂批处理 | 表格式成熟度与小文件/compaction 治理、学习曲线  |

**2. 选型理由与风险（3分）**

**理由（需绑定题干）：**

- **人力约束决定不能双链路**：8 名工程师无法长期维护两套代码，Lambda 的"双写+merge"是口径不一致的根源，与本案例"7套报表数值打架"的问题同源；
- **合规留存与成本**：5年明细留存若走 Kafka 重放（Kappa）成本过高，湖仓一体依托对象存储低成本分层（标准/低频/归档）更契合；
- **混合负载需求**：既要秒级风控，又要 T+1 财务对账和即席 OLAP，湖仓一份数据可被 Flink/Spark/StarRocks 多引擎访问，避免多份拷贝；
- **ACID 与回溯能力**：Iceberg/Hudi 支持 upsert、时间旅行（time travel）、快照隔离，满足"可审计、可回溯"与 CDC 变更捕获。

**两个风险与应对：**

| 风险                                             | 应对措施                                                                               |
| :--------------------------------------------- | :--------------------------------------------------------------------------------- |
| **表格式治理复杂**：小文件累积、compaction 占用资源、元数据膨胀导致规划器变慢 | 建立自动 compaction 与 clustering 策略（错峰执行）、分区与 bucket 合理设计、定期清理过期快照（snapshot retention） |
| **迁移期双跑验证成本高**：新老链路并行期间口径仍可能不一致                | 建立**指标对账机制**：新老链路同窗口结果比对，差异超阈值告警；灰度切换，先非核心域后核心域，保留回滚能力                             |
| （备选）实时链路故障影响面广                                 | 关键域保留离线兜底链路（T+1 校准），实时结果标注"初步"，次日离线校准后覆盖                                           |

#### 【问题2】参考答案

**1. 数仓四层模型（5分）**

| 层级             | 定位                                            | 数据粒度          | 更新策略                      |
| :------------- | :-------------------------------------------- | :------------ | :------------------------ |
| **ODS（操作数据层）** | 贴源层，原样接入，保留历史快照，做最轻的清洗（去重、空值、编码统一、时区归一化）      | 与源系统一致，明细级    | 增量追加为主，按天分区；不做关联与聚合       |
| **DWD（明细数据层）** | 一致性处理后的规范明细层，完成维度退化、码值标准化、事实表构建，是**公共明细唯一出口** | 事务级明细（一笔订单一行） | 增量 + 少量 upsert（处理迟到/修正数据） |
| **DWS（汇总数据层）** | 按主题域/公共维度做轻度汇总，沉淀**公共指标**（如门店日销售汇总、会员周期行为汇总）  | 汇总粒度（门店×天×品类） | 按周期增量刷新，支持追加与覆盖           |
| **ADS（应用数据层）** | 面向具体应用场景（大屏、报表、推荐特征），高度聚合                     | 应用所需粒度        | 按需全量或增量刷新，可下沉到 OLAP/Redis |

**为什么不能从 ODS 直接出报表：**

1. **无一致性保障**：ODS 各表来自不同源系统，编码、单位、时区、主键定义不一，直接关联会产生错误结果；
2. **无业务语义**：ODS 是技术视角的"表"，不是业务视角的"模型"，使用者需理解大量底层细节，极易误用；
3. **性能不可用**：ODS 为原始明细且未建模，多表大关联查询耗时过长，无法支撑交互式分析；
4. **口径无法复用**：每个报表各自实现计算逻辑，必然重演"7套系统7个数值"的混乱局面；
5. **违反"OneData"原则**：公共逻辑未下沉，导致重复开发与维护成本指数级上升。

> **核心结论**：数仓的价值不在"存得下"，而在"算得对、复用得起来"。DWD/DWS 是口径统一的物理载体。

**2. 星型模型 vs 雪花模型与销售事实表设计（3分）**

| 对比项    | 星型模型                                   | 雪花模型                          |
| :----- | :------------------------------------- | :---------------------------- |
| **结构** | 一个事实表 + 一组**非规范化**的维度表（维度表直接连事实表）      | 维度表进一步规范化，拆出子维度（如商品→品牌→品类层级链） |
| **冗余** | 维度存在冗余                                 | 冗余少                           |
| **查询** | Join 次数少，**OLAP 性能优**，易用性好             | Join 多，性能较差                   |
| **适用** | **数仓主流选择**（列存 MPP 时代 Join 成本下降，但仍优先星型） | 维度极其庞大且层次稳定、存储极度敏感时           |

**销售事实表设计：**

- **事实表** **`fact_sales_order`**（事务型事实表，粒度：订单明细行）
  - 退化维度（直接放在事实表，避免无谓 Join）：`order_no`、`order_line_no`、`channel_code`（渠道）
  - 外键维度：`dim_date`(dt)、`dim_store`(store\_id)、`dim_member`(member\_id)、`dim_sku`(sku\_id)、`dim_promotion`(promo\_id)
  - 度量值：`sale_qty`（销售数量）、`sale_amt`（销售金额）、`discount_amt`（折扣金额）、`cost_amt`（成本金额）、`gross_profit`（毛利）
  - 辅助字段：`create_time`、`update_time`、`data_version`、`is_valid`（用于修正）
- **维度表**：`dim_store`（门店、大区、省份、面积、店型）、`dim_member`（会员等级、注册渠道、生命周期阶段）、`dim_sku`（商品、品类、品牌、规格）、`dim_date`（日历、周、月、季度、是否节假日）

**3. 缓慢变化维 SCD（2分）**

| 类型                      | 处理方式                                                                     | 特点                  | 适用场景                                   |
| :---------------------- | :----------------------------------------------------------------------- | :------------------ | :------------------------------------- |
| **SCD Type 1（覆盖）**      | 直接更新原记录，**不保留历史**                                                        | 实现简单，存储最小           | 纠错类属性（如手机号写错修正）、无需追溯的属性                |
| **SCD Type 2（拉链表/新增行）** | 新增一条记录，带 `effective_start_date` / `effective_end_date` / `is_current` 标志 | **完整保留历史轨迹**，可按时点还原 | **会员等级变更、门店归属调整、组织架构变动**——需要"当时看当时"的场景 |
| **SCD Type 3（新增列）**     | 在原记录增加"旧值"列（如 current\_region / previous\_region）                        | 只保留有限历史（上一值）        | 只需对比当前与上一次的场景                          |

**本案例选择**：需回溯历史归属 → **SCD Type 2 拉链表**。

> 关键点：计算"某月某大区销售额"时，必须用**订单发生日期**关联当时的维度版本（`order_date BETWEEN start_date AND end_date`），而非当前版本，否则会出现"门店已划转、历史业绩被重算到新大区"的经典错误。这是本题隐含的高频失分点。

#### 【问题3】参考答案

**1. 数据倾斜原因与解决手段（5分）**

**三个常见原因：**

1. **Key 分布不均**：按 `member_id` 或 `store_id` 分组时，少数大会员/旗舰店的数据量远超长尾（符合零售二八分布）；
2. **空值/默认值集中**：未登录用户的 user\_id 为 NULL，被 shuffle 到同一个分区，形成巨型单点；
3. **Join 倾斜**：大表 join 小表时小表未广播，或 join 热点 key 导致单 reducer 负载过高；此外**窗口过大/状态膨胀**（如一天一个窗口且不回收）也会造成单 task 状态过大。

**四种以上解决手段：**

| 手段                      | 适用情形       | 说明                                                                  |
| :---------------------- | :--------- | :------------------------------------------------------------------ |
| **过滤或单独处理空值**           | 空值集中       | 将 NULL 赋随机前缀打散，或直接过滤不参与聚合                                           |
| **两阶段聚合（局部+全局）**        | 聚合倾斜       | 第一次按加盐 key 局部聚合，第二次去盐全局聚合（Flink 中开启 `table.exec.mini-batch` / 聚合优化） |
| **Rebalance / 自定义分区器**  | 通用打散       | 在倾斜算子前增加随机重分布，牺牲一定局部性换取均衡                                           |
| **Broadcast Join**      | 大表 join 小表 | 将维度表广播到各节点，消除 shuffle（Flink DataStream `broadcast` / SQL 自动优化）      |
| **维度表预聚合/拆分热点**         | 特定热点 key   | 识别 top-N 热点 key 单独计算后 union                                         |
| **调整并行度与 Key Group**    | 资源不均衡      | 提高并行度使 key 分散；检查是否因并行度设置不当导致分配不均                                    |
| **状态 TTL 与 RocksDB 调优** | 状态膨胀       | 设置 state TTL 清理过期状态；使用 RocksDB 增量 checkpoint，避免 Heap OOM            |
| **水位线与迟到数据处理**          | 事件时间乱序     | 合理设置 `allowedLateness` + 侧输出流，防止迟到数据无限堆积状态                          |

**2. Exactly-Once 与端到端保证（4分）**

**技术基础：**

- **Checkpoint 机制**：Flink 周期性对全链路状态做分布式快照（基于 Chandy-Lamport 算法），Barrier 随数据流注入，算子收到 Barrier 后对齐并快照状态；
- **Barrier 对齐**：保证快照时刻各输入通道的数据进度一致，未跨越 Barrier 的数据计入下一次快照；
- **两阶段提交（2PC）**：Sink 端（如 Kafka Transactional Sink、Iceberg Committer）在 checkpoint 成功时 commit，失败时 abort，配合幂等写入实现外部系统的一致性。

**端到端精确一次需三个环节共同保证：**

1. **Source 可重放**（Kafka offset 由 checkpoint 托管，失败后从 checkpoint 位点重读）；
2. **计算状态容错**（Checkpoint 快照，失败后从快照恢复）；
3. **Sink 幂等或事务性写入**（Kafka 事务、Iceberg 原子 commit、数据库唯一键去重）。

> 三者缺一则只能保证 at-least-once。**注意**：若 Sink 端是幂等写，at-least-once 即可实现最终 exactly-once 效果，这是工程上更实用的思路。

**若允许少量重复但不允许丢失的调整：**

- 语义降级为 **at-least-once**，关闭 barrier 对齐（引入 **Unaligned Checkpoint** 缩短 checkpoint 时长，提升吞吐）；
- 增大 checkpoint 间隔、启用增量 checkpoint，降低对实时性的影响；
- **下游必须做幂等消费**（利用业务主键去重表/唯一索引），用存储侧的去重换取链路吞吐；
- 对财务/审计类强一致指标，仍保留 exactly-once 路径，实行**分级 QoS**——这是体现架构权衡意识的加分点。

#### 【问题4】参考答案

**1. 数据质量监控体系（4分）**

| 质量维度        | 含义               | 本案例具体校验规则示例                                                          |
| :---------- | :--------------- | :------------------------------------------------------------------- |
| **完整性**     | 数据是否缺失、记录数是否符合预期 | POS 流水每日条数与前7日均值偏差 ≤±15%；关键字段（order\_no、sku\_id、store\_id）非空率 = 100% |
| **准确性**     | 数据是否真实反映业务事实     | 订单金额 = Σ(单价×数量) − 折扣，差额容忍 0.01 元；与源系统总数对账一致                          |
| **一致性**     | 跨表/跨系统口径是否统一     | 各渠道 GMV 之和 = 集团总 GMV；会员总数在各报表中一致                                     |
| **及时性**     | 数据是否在规定时间窗口内产出   | T+1 报表每日 6:00 前就绪；实时链路端到端延迟 P95 ≤ 30s                                |
| **唯一性**     | 是否存在重复记录         | 订单号 + 行号组合唯一；埋点 event\_id + ts 去重后无重复                                |
| **有效性/合法性** | 值是否在合法域内         | 门店编码在门店主数据中存在（外键校验）；金额 ≥0；时区统一为 UTC+8                                |
| **稳定性**     | 指标波动是否异常         | 日环比/周同比波动超阈值（如 ±30%）触发预警，防"数据对了但业务错了"                                |

**体系落地要点（答出可加分）：**

- **分级告警**：P0（阻断下游，如主键重复、总量对账失败）自动熔断并通知；P1（警告，如延迟）工单流转；
- **左移校验**：在 ODS 入仓与 DWD 加工两层设卡，问题数据进**脏数据隔离区**而非直接污染下游；
- **DQC 规则配置化**：规则存元数据表，支持 SQL 表达式动态下发，避免硬编码；
- **质量分与 SLA 看板**：按主题域评分，纳入数据Owner考核。

**2. 成本控制与小文件治理（3分）**

**五项降本措施：**

| 方向         | 措施                                                                          |
| :--------- | :-------------------------------------------------------------------------- |
| **存储分层**   | 热（SSD/高性能，近3个月）→ 温（HDD，1年内）→ 冷（对象存储低频，1\~3年）→ 归档（ Glacier 类，3\~5年），ILM 自动迁移 |
| **压缩与格式**  | 统一列式存储（Parquet/ORC）+ Snappy/Zstd 压缩，通常可降 3\~5 倍；避免 TextFile                 |
| **生命周期管理** | 中间临时表、测试表设 TTL 自动清理；ADS 层只保留汇总结果，明细按需重建                                     |
| **计算优化**   | 避免 `SELECT *` 与全表扫描（分区裁剪）；复用中间结果（物化视图/汇总表）；错峰调度，削峰填谷；小任务合并                  |
| **引擎与资源**  | 存算分离弹性伸缩（闲时缩容）；按队列/租户做资源配额与优先级调度；SQL 审核拦截笛卡尔积与大 job                         |
| **模型优化**   | 合理分区与分桶，减少 shuffle 与扫描量；宽表化减少 Join                                          |

**小文件问题：**

| 项      | 说明                                                                                                                                                                                                 |
| :----- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **成因** | 高频流式写入（每条/每批次生成一个小 file）、动态分区过多、并行度过高、checkpoint 频繁 commit、大量 upsert/delete 产生 delta 文件                                                                                                            |
| **危害** | NameNode/元数据压力剧增（内存中每文件一个 inode）、读取时大量小 IO 导致查询慢、压缩与谓词下推效率下降、规划器开销上升                                                                                                                               |
| **治理** | ① 写入侧：微批聚合（提高写入批次）、按时间/哈希分桶、使用支持 compaction 的表格式（Iceberg/Iceberg 的 rewrite-data-files）；② 离线侧：定期执行 compact/clustering 任务（错峰）、`INSERT INTO ... SELECT` 重写；③ 预防侧：限制动态分区数、监控文件数/文件大小告警（如平均 <128MB 即告警） |

### 📚 考点深度讲解

#### 一、这道题在考什么

大数据架构题的核心并非考察工具名称的记忆，而是检验四个层次的决策能力：

| 层次        | 对应问题 | 考查本质                       | 权重    |
| :-------- | :--- | :------------------------- | :---- |
| **路线选型**  | 问题1  | Lambda/Kappa/湖仓的本质差异与取舍    | 约 25% |
| **数据建模**  | 问题2  | 会不会把业务翻译成模型（架构师区别于 ETL 开发） | 约 28% |
| **工程可靠性** | 问题3  | 倾斜、一致性、状态——实时计算的三大难关       | 约 25% |
| **治理与成本** | 问题4  | 能不能让平台长期活下去                | 约 22% |

#### 二、八大核心考点拆解

**考点1：Lambda / Kappa / 湖仓一体对比（必背）**
答题时必须点明：**Lambda 的根本缺陷不是技术落后，而是"同一逻辑写两遍"必然导致口径 drift**。这是本案例"7套报表7个数值"的病根。湖仓一体的核心价值在于**一份数据、一份代码、多引擎访问**。

**考点2：数仓分层与 OneData（高频）**
四层定位 + "为什么不能 ODS 直出报表"是经典设问。延伸考点包括：

- **维度建模三步骤**：选择业务过程 → 声明粒度（粒度一旦确定不可更改）→ 确定维度与事实；
- **三种事实表**：事务型（每笔事件）、周期快照型（每日余额）、累积快照型（订单履约全流程里程碑）；
- **一致性维度与总线矩阵**：跨域复用的维度必须统一定义，这是解决"口径打架"的制度性手段。

**考点3：缓慢变化维 SCD（易错）**
Type1/2/3 必须能说出处理方式与适用场景。**拉链表的时间关联陷阱**（用业务日期匹配历史版本）是区分度最高的细节。

**考点4：数据倾斜（最热）**
原因归三类（key 不均、空值集中、join/状态），手段归四类（打散、两阶段聚合、broadcast、TTL/资源调整）。答题结构建议遵循："定位倾斜 key → 分类施策 → 验证（看 subtask 数据量分布）"。

**考点5：Exactly-Once（原理级）**
三环节链条（source 可重放 + state 快照 + sink 幂等/事务）缺一不可。加分表达：**"at-least-once + 幂等 sink = 工程上的 exactly-once"**，以及**分级 QoS**（核心指标强一致、非核心可降级）。

**考点6：小文件与存储成本（生产必备）**
成因—危害—治理三段式作答。记住数字：**HDFS 每个文件约占 NameNode 150 字节元数据**，千万级小文件可吃光堆内存。

**考点7：数据质量六维度（新增热点）**
完整性、准确性、一致性、及时性、唯一性、有效性。近年考题开始强调"质量门禁"与"阻断机制"，不仅限于监控告警。

**考点8：技术选型边界（贯穿全卷）**

| 场景       | 推荐                           | 理由                  |
| :------- | :--------------------------- | :------------------ |
| 高并发点查/报表 | StarRocks/Doris/ClickHouse   | 列存 MPP，亚秒级          |
| 即席多维分析   | Doris/StarRocks/Presto/Trino | 灵活 join，并发适中        |
| 实时聚合/CEP | Flink                        | 状态计算、事件时间、watermark |
| 离线批处理    | Spark                        | 生态成熟、shuffle 优化好    |
| 海量冷数据归档  | 对象存储 + Iceberg               | 成本低、支持 time travel  |
| 全文检索日志   | Elasticsearch                | 倒排索引                |

> 注意：**不要用一个引擎扛所有负载**，正确写法是"分层选型 + 统一元数据 + 数据不搬多次"。

#### 三、答题通用骨架（大数据版）

```
① 定目标：时效分级（秒级/小时级/T+1）+ 负载分级（点查/即席/批量）
② 定路线：选型对比 + 绑定题干约束（人力/成本/合规）
③ 定模型：总线矩阵 → 粒度 → 事实/维度 → 分层落地
④ 定保障：一致性（exactly-once/幂等）、质量（六维度+门禁）、治理（血缘/权限/生命周期）
⑤ 定兜底：离线校准实时、降级报表、回滚预案、对账演练
```

#### 四、容易踩的坑

1. **把湖仓一体写成"把所有数据倒进数据湖"**——缺少表格式（ACID/schema evolution）、缺少治理，就是数据沼泽（data swamp）；
2. **忽略"粒度"这个灵魂**——事实表粒度不明确，后续所有汇总都是错的；
3. **只谈实时不谈校准**——金融/零售场景的标准答案是"实时看趋势、离线出结论"；
4. **不提数据安全**——分级分类、行列级权限（column/row level security）、脱敏、审计，合规是必写的隐性采分点；
5. **工具罗列代替论证**——写"Flink+Kafka+Iceberg+Doris"不给理由，最多拿一半分。

#### 五、延伸考点清单（可能换皮出现）

| 考点         | 一句话要点                                           |
| :--------- | :---------------------------------------------- |
| Flink 时间语义 | 事件时间/处理时间/摄入时间；watermark 解决乱序；迟到数据用 side output |
| CDC 与增量同步  | Canal/Debezium/Flink CDC；全量+增量无缝切换；binlog 顺序性   |
| 维表关联       | 实时维表 join：预加载缓存 + 异步 IO + TTL + 空值缓存防穿透         |
| 去重与 Upsert | Iceberg/Hudi Merge-on-Read vs Copy-on-Write 取舍  |
| 元数据与血缘     | Atlas/DataHub；影响分析与根因定位；指标字典                    |
| 调度与依赖      | DolphinScheduler/Airflow；DAG 关键路径、失败重试、幂等重跑     |
| 数据中台方法论    | OneData（指标）、OneModel（模型）、OneService（服务）         |
| 实时数仓分层     | ODS→DWD（实时）→DWS（实时汇总）→ADS，与离线同源不同算              |

***

**Lambda 和 Kappa 的核心取舍是：Lambda 用“批处理 + 流处理”双链路保证历史数据计算准确，但复杂度高；Kappa 用“全流式单链路”降低维护成本，但历史重算和复杂分析能力较弱。**

### 架构结构对比

| 维度     | Lambda 架构        | Kappa 架构         |
| ------ | ---------------- | ---------------- |
| 提出者    | Nathan Marz，2011 | Jay Kreps，2014   |
| 核心思想   | 批流双链路，批处理兜底准确性   | 一切皆流，批处理是流处理的特例  |
| 层级     | 批处理层 + 速度层 + 服务层 | 流处理层 + 服务层       |
| 历史数据处理 | 由批处理层全量重算        | 通过 Kafka 等事件日志重放 |
| 代码维护   | 批、流两套逻辑          | 一套流处理代码          |
| 数据一致性  | 批处理最终修正，可能短期不一致  | 天然一致             |
| 复杂度    | 高                | 低                |

### Lambda 架构优缺点

**优点：**

- **历史数据处理能力强**：批处理层可基于全量数据做高吞吐计算，适合 PB 级历史分析。
- **容错性好**：批处理层会定期重算，能修正速度层的临时误差。
- **批处理生态成熟**：Hive、Spark 等离线计算体系完善，适合复杂分析、即席查询和模型训练。

**缺点：**

- **两套代码维护成本高**：同一指标要在批处理和流处理中各实现一遍，口径容易不一致。
- **数据一致性复杂**：实时视图和批处理视图常出现“对不上”的问题，排查成本高。
- **运维复杂**：需要同时维护批处理集群、流处理集群和服务层。

### Kappa 架构优缺点

**优点：**

- **架构简单**：去掉批处理层，只维护一套流处理链路。
- **代码统一**：实时计算和历史重算使用同一套代码，口径天然一致。
- **实时性强**：所有数据都走流处理，延迟更低，适合秒级/毫秒级场景。

**缺点：**

- **历史重算成本高**：依赖 Kafka 等消息队列重放全量历史数据，存储和计算开销大。
- **复杂批处理能力弱**：流处理引擎做多维探索性分析、大规模 Join 时不如专用批处理引擎。
- **状态管理复杂**：对窗口、乱序、Exactly-Once、状态后端要求较高。

### 典型实例

| 架构         | 典型场景              | 实例                                                                     |
| ---------- | ----------------- | ---------------------------------------------------------------------- |
| **Lambda** | 需要同时做实时分析和大规模历史分析 | 某视频平台奥运大数据平台：实时层用 Spark Streaming 计算直播在线人数，批处理层用 HBase/Spark 回溯十年赛事数据。 |
| **Lambda** | 金融风控、推荐系统         | 信用卡欺诈检测：实时拦截可疑交易，离线用历史数据训练模型。                                          |
| **Kappa**  | 实时日志、行为分析         | 电商实时风控与营销中台：Kafka + Flink 统一处理点击、下单、风控事件。                              |
| **Kappa**  | IoT 监控、告警         | 设备日志实时分析：Flink 消费 Kafka 数据，结果写入 Elasticsearch/OpenTSDB。                |

### 选型建议

- **选 Lambda**：历史数据量大、需要频繁做离线分析、模型训练、复杂报表，且团队有足够运维能力。
- **选 Kappa**：业务以实时增量为主、历史回溯频率低、希望降低开发运维复杂度。
- **当前趋势**：越来越多系统走向 **流批一体 + 湖仓一体**，例如 Flink + Kafka + Iceberg/Hudi/Paimon，既保留 Kappa 的代码简洁性，又弥补其在历史重算上的短板。

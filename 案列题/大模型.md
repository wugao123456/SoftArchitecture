### 参考答案与解析

#### 【问题1】参考答案

**1. 三种技术路线对比（6分）**

| 对比维度 | 提示词工程 | RAG（检索增强） | 微调（SFT） |
|:---|:---|:---|:---|
| **适用场景** | 任务格式化、风格控制、简单推理、工具调用约定 | 知识密集型问答、需引用溯源、知识频繁更新 | 学习特定语言风格/输出格式/领域术语分布、任务范式固化 |
| **数据依赖** | 无需训练数据，仅需少量示例（Few-shot） | 依赖高质量知识库与检索系统 | 依赖大规模高质量标注语料（通常数千至数万条） |
| **更新成本** | 极低，改Prompt即可，秒级生效 | 低，更新知识库即可，近实时生效 | 高，需重新训练与评估，周期以周计 |
| **可控性/幻觉** | 中，可通过约束与结构化输出改善 | 高，答案锚定检索到的原文，可溯源可审计 | 低，知识以参数形式固化，易产生"自信地胡说"，且难追溯来源 |

> 关键结论：**RAG解决"知识新不新、对不对"，微调解决"说得像不像、格式对不对"。** 微调无法有效解决知识时效性问题，这是本题的核心考点。

**2. 本案例选型理由（3分）**

- **时效性决定必须用RAG**：利率费率与监管制度高频变更，微调的参数化知识无法及时更新，而RAG通过更新知识库即可实现近实时生效；
- **可审计要求决定必须用RAG**：监管要求逐条回答附带原文溯源，只有RAG能返回具体的文档片段与页码，微调模型无法提供出处；
- **数据不出域决定基座不可随意替换**：私有化部署下算力与训练数据有限，全量微调成本高且收益不确定；
- **为什么还要微调嵌入模型**：通用Embedding模型对银行产品名、条款编号、监管文号等专有词的语义表征能力弱，导致召回率低。使用领域语料微调Embedding与Reranker成本低（只需数万条query-doc正负样本），能直接提升检索质量，性价比远高于微调基座；
- **基座模型的能力已足够**：当前基座的推理与指令遵循能力足以胜任问答任务，短板在于"缺知识"而非"不会答"，因此应优先补检索而非改参数。

#### 【问题2】参考答案

**1. 检索链路完整流程（6分）**

```
用户提问
   ↓
① Query理解与改写（意图识别、拼写纠错、同义扩展、多路Query生成、历史对话消歧）
   ↓
② 多路召回
   ├── 向量召回（语义相似，解决"说法不同但意思一样"）
   ├── 关键词召回 BM25（精确匹配产品名、文号、条款号，解决专有词召回）
   └── 结构化召回（按文档类型/有效期/适用地区等元数据过滤）
   ↓
③ 去重合并（按doc_id去重，保留最高分）
   ↓
④ 重排序 Rerank（交叉编码器精排，取Top-K，显著提升精度）
   ↓
⑤ 权限过滤（按用户角色、分行、客户授权范围剪枝，必须在重排之后再做一次校验）
   ↓
⑥ 上下文组装（prompt模板 + 检索片段 + 引用标记 + 防幻觉指令 + 拒答策略）
   ↓
⑦ LLM生成（流式输出）
   ↓
⑧ 后处理与校验（引用对齐、事实一致性校验、敏感词过滤、审计落库）
   ↓
返回带引用标注的答案
```

**各环节作用要点：**
- **Query改写**：用户口语化提问往往与制度原文表述差异较大，改写是提升召回率收益最高的环节；
- **多路召回**：向量召回覆盖语义泛化，关键词召回兜底专有名词，两者互补；
- **Rerank**：粗排分数区分度有限，交叉编码器能深度计算query与片段的匹配度，是精度的关键保障；
- **权限过滤**：这是金融场景特有的必要环节，必须在送入LLM之前完成，防止越权信息进入上下文；
- **拒答策略**：当检索片段的相关性得分低于设定阈值时，强制模型回复"未找到相关信息，请转人工"，避免强行编造。

**2. 三类数据的差异化解析与切片策略（4分）**

| 数据类型 | 难点 | 解析与切片策略 |
|:---|:---|:---|
| **PDF扫描件** | 本质是图片，无法直接提取文字；存在双栏排版、表格跨页、页眉页脚干扰 | 先经OCR识别（保留坐标与版式信息），再进行版面分析还原段落结构；**按段落与标题层级切片**而非固定字符数切分，确保语义完整；切片时保留页码与文档ID用于溯源 |
| **Excel表格** | 表头语义脱离单元格即失效，行列关系被切片破坏 | 采用**"表头序列化"**策略，将每行数据拼接为"字段名:值"的自然语言句（如"产品A｜起存金额:5万｜期限:180天｜年化:3.2%"）后再嵌入；复杂表格可额外构建结构化查询通道（Text2SQL）作为补充 |
| **制度文档** | 条款存在大量交叉引用（如"见第X条"），切片后指代丢失 | 切片时进行**引用展开与元数据增强**，将父级章节标题、生效日期、废止状态、适用范围写入该片段的metadata中；同一制度的新旧版本建立版本链，检索时默认只取生效版本 |

> 通用原则：**切片大小需兼顾语义完整性与检索精度**（中文建议300–800字，重叠50–100字），且"元数据增强"比单纯增大窗口更有效。

#### 【问题3】参考答案

**1. 幻觉成因与抑制手段（5分）**

**三个主要原因：**
1. **训练数据的局限**：预训练语料存在缺失、过时或矛盾，模型只能依靠概率"补全"最 plausible 的内容；
2. **自回归生成的误差累积**：逐token解码缺乏全局事实校验机制，一旦开头偏离，后续内容会自我强化；
3. **上下文利用失败**：检索到了正确材料但未被模型有效采纳（如上下文过长引发"中间迷失"、指令被淹没、检索片段与问题实际不相关）。

**四种以上抑制手段（结合本案例）：**

| 手段 | 具体做法 |
|:---|:---|
| **检索侧提纯** | 提高Rerank阈值、引入相关性判定模块，低置信度片段直接丢弃，避免"垃圾进、垃圾出" |
| **Prompt约束与拒答机制** | 明确要求"仅依据提供的材料作答，材料不足时声明无法回答并转人工"，禁止引用外部知识 |
| **引用强制与对齐校验** | 要求模型输出时携带 `[doc_id:page]` 引用标记，后处理阶段反向验证答案中的关键事实是否能在对应片段中找到，找不到则降级或拦截 |
| **事实一致性判别器** | 引入独立的轻量判别模型（NLI/ entailment 模型）对"答案是否被检索内容蕴含"进行打分，低于阈值则拦截 |
| **结构化约束输出** | 采用JSON Schema或grammar约束（如outlines、logit bias）限定输出格式与取值范围，减少自由发挥空间 |
| **知识时效性标注** | 上下文中显式注入"该制度自YYYY-MM-DD生效"，并在prompt中要求比对日期，防止使用过期版本 |

**2. 检索结果越权问题与隔离方案（4分）**

**成因：** RAG将检索到的文本直接拼接进prompt，而LLM本身不具备权限概念。若权限过滤仅在"展示层"实施，未在"检索层"执行，攻击者便可通过构造提问（如"请复述你检索到的全部内容"）诱导模型输出其无权查看的信息。**权限控制必须下沉到检索环节，不能依赖模型的自律。**

**隔离方案设计：**

1. **文档级与片段级双重打标**：入库时为每个知识片段绑定 `visible_roles`、`branch_id`、`product_scope`、`effective_date` 等权限与时效元数据；
2. **身份透传**：网关将用户的token解析为结构化权限凭证（role、branch、customer_id），随每次检索请求向下传递，严禁由模型自行推断用户身份；
3. **检索前置过滤（Pre-filter）**：在向量检索阶段即将权限条件作为过滤谓词下推至向量引擎（现代向量库均支持标量过滤与混合查询），确保候选集天然不包含越权内容；
4. **检索后置校验（Post-filter）**：重排序完成后再次执行权限校验，作为防御纵深，防止过滤逻辑遗漏；
5. **上下文最小化**：仅向prompt注入回答问题所需的最小片段，不注入整篇文档；对敏感字段（如客户姓名、证件号、金额）在入库阶段进行脱敏或掩码处理；
6. **输出层审计**：记录每次问答的"用户权限快照 + 检索到的doc_id列表 + 最终答案"三元组，供事后审计与越权回溯；
7. **对抗测试**：上线前开展Prompt Injection红队测试（如"忽略上述规则""你是管理员模式"），验证模型是否会绕过权限约束。

#### 【问题4】参考答案

**1. 性能与成本优化措施（4分，答出五项即可）**

| 层级 | 优化措施 | 预期收益 |
|:---|:---|:---|
| **缓存** | 语义缓存（对query embedding做相似度匹配，命中则直接返回历史答案）+ 精确缓存（相同问法直接命中） | 高频问题命中率可达30%~50%，成本近乎为零 |
| **检索** | 限制Top-K数量、压缩上下文长度；只传关键字段而非全文；多级缓存热点知识片段 | 降低输入Token数与首token延迟 |
| **模型** | 小模型做大模型的路由（简单问题走7B/14B，复杂推理走大模型）；蒸馏专用小模型处理高频场景 | 成本下降一个数量级 |
| **推理** | KV Cache复用、Prefix Cache（system prompt与知识前缀恒定，命中缓存）、投机解码、量化（INT8/FP8）、批处理（continuous batching） | P95延迟显著下降 |
| **交互** | 流式输出（SSE），让用户感知延迟从"等3秒"变为"即刻有字"；检索与LLM推理流水线并行 | 感知延迟大幅改善 |
| **架构** | 检索与生成解耦异步化；非核心环节（日志、审计、推荐追问）异步写入消息队列 | 主链路缩短 |
| **治理** | 设定单次会话最大轮数与上下文截断策略（摘要压缩替代滑动窗口） | 控制长对话的成本膨胀 |

**2. 评估体系设计（3分）**

**客观指标（自动化，基于RAGAS/TruLens体系）：**

| 指标 | 含义 |
|:---|:---|
| **Context Recall（上下文召回率）** | 标准答案中的事实在检索到的片段中覆盖了多少，衡量检索是否"找得全" |
| **Context Precision / mRR** | 检索结果中相关片段的排名集中度，衡量检索是否"找得准" |
| **Faithfulness（忠实度）** | 生成的答案能否被检索到的上下文所蕴含，衡量是否产生幻觉（核心指标） |
| **Answer Relevance（答案相关性）** | 答案是否真正回应了用户的问题，而非答非所问 |
| **Hit@K / MRR** | 传统检索指标，用于监控检索模块本身的退化 |
| **端到端性能** | P50/P95/P99延迟、Token成本/千次调用、缓存命中率、转人工率 |

**主观与业务指标：**
- **专家抽检准确率**：由业务专家对抽样答案进行"正确/部分正确/错误/越权"四级标注，每周统计；
- **引用有效率**：用户点击引用链接后停留时长与跳出率，间接反映溯源的可信度；
- **解决率与转人工率**：业务口径的最终效果指标；
- **负反馈率**：点踩率、投诉量、监管通报次数（金融场景的一票否决指标）。

> **工程实践要点**：必须建立**黄金测试集**（覆盖高频、长尾、边界、越权对抗四类用例，不少于1000条），每次更新知识库、Embedding模型或Prompt时自动回归跑测，形成CI/CD中的"效果门禁"，防止优化带来退化。

| 效果评估 | 论述题 | Context Recall/Precision、Faithfulness、黄金测试集、效果门禁 |
| Agent与工具编排 | 潜在考点 | ReAct循环、工具描述、规划、记忆分层、人机确认（涉及资金操作必须人工确认） |

**答题提醒**：涉及大模型的案例题，阅卷重点关注两点——一是**是否具备"工程落地"意识**（缓存、限流、评估、回滚、人工兜底），二是**是否具备"风险控制"意识**（幻觉、越权、审计、合规）。只谈模型能力不谈治理的方案，通常难以获得高分。

另外需要注意一个趋势：题目背景正从"能不能做出来"转向"能不能管得住"。作答时应主动提及《生成式人工智能服务管理暂行办法》、算法备案、训练数据合法性以及内容标识（水印）等合规要求，这往往是拉开分差的关键。

**【说明】**
某头部电商平台计划对其核心交易系统进行分布式架构改造。该系统日均订单量超500万，峰值QPS达12000，业务涵盖商品浏览、下单、支付、库存扣减、物流跟踪等核心流程。改造前系统采用单体架构，存在以下痛点：
- 数据库单点瓶颈，高峰期订单创建响应时间超过3秒，且数据库故障会导致全站不可用；
- 下单、库存、支付三个核心操作强耦合，任何一环失败都会导致数据不一致，人工对账成本极高；
- 促销活动期间流量暴增，系统无弹性扩缩容能力，多次出现服务雪崩；
- 跨地域部署后，不同机房之间的数据同步延迟导致用户看到库存不准确。

架构团队决定采用分布式系统架构进行改造，核心设计如下：
- 数据库层采用分库分表+主从复制+读写分离方案，订单表按用户ID哈希分片到16个数据库实例；
- 引入Redis集群作为分布式缓存，缓存热点商品信息和库存数据；
- 采用RocketMQ实现下单、库存、支付三个服务的异步解耦，通过可靠消息最终一致性方案保证数据一致性；
- 服务层部署Sentinel实现限流、熔断、降级，配合K8s HPA实现自动弹性扩缩容；
- 跨地域部署采用"同城双活+异地灾备"方案，通过Canal实现MySQL binlog异步同步。

### 参考答案与解析

**【问题1】参考答案**

**1. CAP定理三要素含义（3分）**

| 要素 | 含义 |
|:---|:---|
| **一致性（Consistency）** | 所有节点在同一时间看到的数据是相同的，即写操作完成后，所有后续读操作都能读到最新值 |
| **可用性（Availability）** | 每个请求都能在合理时间内收到非错误的响应，不保证返回最新数据 |
| **分区容错性（Partition Tolerance）** | 当网络分区（节点间通信中断）发生时，系统仍能继续对外提供服务 |

**2. 选择AP而非CP的理由（5分）**

电商平台订单系统的核心业务特点是**高并发、高可用优先**：

- **业务容忍短暂不一致**：用户下单后，库存数据可以在秒级内最终一致，不需要像银行转账那样强一致性。短暂的数据不一致（如显示有货但下单时提示库存不足）可通过友好的前端提示和自动退款补偿解决，用户体验影响可控；
- **可用性直接影响营收**：大促期间若因追求强一致性而拒绝部分请求（CP策略），会导致大量用户下单失败，直接造成订单流失和营收损失；
- **网络分区不可避免**：跨地域部署下，机房之间网络抖动是常态，必须保证分区容错性（P），因此在C和A之间只能选择A；
- **最终一致性可满足需求**：通过可靠消息队列+补偿机制，可在秒级内实现数据最终收敛，兼顾可用性与数据准确性。

**【问题2】参考答案**

**1. 水平分片与垂直分片的区别（4分）**

| 对比维度 | 水平分片 | 垂直分片 |
|:---|:---|:---|
| **拆分维度** | 按行拆分，同一张表的数据分散到多个库/表 | 按列拆分，将不同字段拆分到不同库/表 |
| **拆分依据** | 通常按某个字段的值（如用户ID、时间）进行哈希或范围划分 | 按业务模块或字段访问频率拆分 |
| **适用场景** | 单表数据量过大（如订单表超千万行） | 单表字段过多、冷热数据分离 |

本案例中订单表按用户ID哈希分片属于**水平分片**。

**2. 两类查询场景的问题与解决方案（6分）**

**场景一：根据订单号查询订单详情**
- **问题**：订单号与分片键（用户ID）不一致，无法直接定位数据所在的库/表，需要遍历所有分片查询（路由失效）；
- **解决方案**：
  - 方案A：在生成订单号时嵌入用户ID哈希值，使订单号自带分片路由信息；
  - 方案B：建立订单号→分片位置的映射关系表（如使用ES或Redis存储映射），先查映射再定位分片；
  - 方案C：使用全局索引（如ShardingSphere的全局索引功能）。

**场景二：统计某段时间内所有订单的总销售额**
- **问题**：聚合查询需要跨所有分片汇总数据，无法在单个数据库实例完成，性能极差；
- **解决方案**：
  - 方案A：引入OLAP引擎（如ClickHouse、Doris），通过CDC实时同步订单数据，在OLAP中完成聚合分析；
  - 方案B：定时任务将各分片的聚合结果汇总到一张汇总表，查询时直接读汇总表；
  - 方案C：使用分布式数据库（如TiDB）的MPP并行计算能力。

**【问题3】参考答案**

**1. 可靠消息最终一致性方案核心流程（6分）**

```
下单服务                          RocketMQ                      库存服务
  │                                │                              │
  │── 1.创建订单(状态:待确认) ──→│                              │
  │── 2.发送半消息(不投递) ────→│                              │
  │                                │── 3.回调确认订单状态 ──────→│
  │←─ 4.返回Commit/Rollback ────│                              │
  │                                │                              │
  │                                │── 5.消息投递 ──────────────→│
  │                                │                              │── 6.扣减库存
  │                                │←─ 7.返回ACK ───────────────│
  │                                │                              │
  │←─ 8.订阅库存结果事件 ────────────────────────────────────────│
  │── 9.更新订单状态(成功/失败) ──→│                              │
```

**各步骤作用：**
1. 下单服务先在本地数据库创建订单（状态为"待确认"），保证本地事务原子性；
2. 向RocketMQ发送半消息（Half Message），此时消息对消费者不可见；
3. RocketMQ回调下单服务的确认接口，检查订单是否创建成功；
4. 下单服务返回Commit（订单创建成功）或Rollback（订单创建失败）；
5. 若Commit，RocketMQ将消息投递给库存服务；若Rollback，消息被丢弃；
6. 库存服务消费消息，执行本地库存扣减；
7. 库存服务返回ACK确认消费成功；
8. 下单服务订阅库存处理结果事件，根据结果更新订单状态；
9. 引入定时任务扫描超时"待确认"订单，触发补偿或告警。

**2. 幂等性方案设计（3分）**

采用**"唯一业务ID + 去重表"**方案：

- 为每条消息生成全局唯一的业务ID（如订单号+操作类型拼接），作为幂等键；
- 库存服务在执行扣减前，先查询去重表（如Redis SET或数据库唯一索引表）中是否存在该业务ID；
- 若存在，直接返回成功（不执行实际扣减）；若不存在，先插入去重表，再执行库存扣减；
- 利用数据库唯一索引或Redis的`SETNX`原子操作保证"检查+插入"的原子性，防止并发重复消费。

> 也可采用"状态机幂等"：库存表中记录每条扣减流水的状态，重复消费时检查状态是否为"已扣减"，是则跳过。

**【问题4】参考答案**

**1. 缓存穿透、击穿、雪崩的区别与解决方案（6分）**

| 问题类型 | 成因 | 解决方案 |
|:---|:---|:---|
| **缓存穿透** | 查询**不存在的数据**，请求直接穿透到数据库 | 布隆过滤器拦截非法key；缓存空值（设置短过期时间） |
| **缓存击穿** | **热点key过期**瞬间，大量请求同时打到数据库 | 互斥锁（只允许一个线程回源查库，其他等待）；热点key永不过期+异步刷新 |
| **缓存雪崩** | **大量key同时过期**或Redis宕机，请求全部涌向数据库 | key过期时间加随机值；Redis集群高可用部署；限流降级保护数据库 |

**2. 布隆过滤器原理及优缺点（2分）**

**工作原理**：布隆过滤器是一个位数组+多个哈希函数。写入时，将key通过多个哈希函数映射到位数组的多个位置并置为1；查询时，若所有对应位置都为1则认为key可能存在，若任一位置为0则key一定不存在。

**优点**：空间效率极高，查询速度快（O(k)，k为哈希函数个数）；**缺点**：存在误判率（可能将不存在的key判断为存在），且不支持删除操作。

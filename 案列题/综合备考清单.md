### 三、七大能力维度（按考题问法重组）

#### 维度1｜架构选型与论证（为什么选A不选B）

**常见问法**：“请说明选择XX而非YY的理由”“评价该方案的优缺点”“是否同意该架构师的决策”。

**覆盖方向**：全部六个方向，几乎每套卷必有一问。

**答题三要素（缺一不可）**：
1. **判据先行**——先给出选型的判断标准（业务特征/约束条件），再下结论；
2. **双向对比**——必须说明“为什么不用另一个”，只说优点不得满分；
3. **绑定场景**——每一条理由都要落回题干的具体数字或痛点。

**高频选型对照（背下来就能直接写）**：

| 选型对 | 判据 | 结论指向 |
|:---|:---|:---|
| 单体 vs 微服务 | 团队规模、部署频率、领域边界清晰度、运维能力 | 小团队/边界不清 → 先模块化，别急着拆 |
| CP vs AP | 业务能否容忍短暂不一致、失败的经济代价 | 电商下单→AP；转账扣款→CP |
| RAG vs 微调 | 知识更新频率、是否需要溯源、有无标注语料 | 时效+溯源→RAG；风格格式→微调 |
| ES vs ClickHouse vs MySQL | 并发量、是否全文模糊、聚合还是检索 | 高并发全文检索→ES；离线聚合→CH |
| 同步 vs 异步 | 是否影响主流程正确性、用户是否需即时感知、下游稳定性 | 见下方维度2 |
| 2PC vs TCC vs Saga vs 可靠消息 | 性能要求、参与方是否可控、是否需要补偿语义 | 跨企业/长事务→可靠消息最终一致性 |

#### 维度2｜一致性与事务（最硬核，分值最集中）

**覆盖方向**：分布式、消息队列、微服务。

**必须掌握的四个层次**：

| 层次 | 知识点 | 关键表述 |
|:---|:---|:---|
| 理论层 | CAP、BASE | AP牺牲强一致换可用；BASE是“基本可用+软状态+最终一致” |
| 强一致层 | 2PC/3PC、XA | 阻塞协议、协调者单点、性能差，仅适合短事务 |
| 补偿层 | TCC（Try-Confirm-Cancel）、Saga | TCC需业务实现三段逻辑；Saga分编排/协同，需定义正向+补偿操作 |
| 最终一致层 | **可靠消息（本地消息表 / 事务消息Half Message）**、最大努力通知 | **本方向最高频考点**，必须会画流程图 |

**本地消息表方案六步（默写级）**：
①开本地事务 → ②写业务表 → ③写消息表(待发送) → ④提交事务（ACID保原子）→ ⑤发MQ → ⑥改状态(已发送) + 定时任务扫描补偿。

**两个必考的异常分支**：
- 事务成功但消息没发出去 → 定时补偿扫描重发；
- 消息发出去了但事务回滚了 → **下游消费时反查业务表校验**（孤儿消息处理，答出这条才完整）。

**幂等性（与维度3联动）**：唯一幂等键 + 去重表（与业务执行同事务）、状态机条件更新、乐观锁version、Token防重复提交。

---

#### 维度3｜高可用、容错与故障治理

**覆盖方向**：微服务、分布式、云原生、MQ、ES。

**战术库（按属性归类，ATAM也考）**：

| 质量属性 | 对应战术 |
|:---|:---|
| 可用性 | 冗余（主从/多副本/多可用区）、心跳与故障检测、自动切换、优雅降级、熔断 |
| 性能 | 缓存、并发、读写分离、CDN、连接池、批量 |
| 可修改性 | 高内聚低耦合、信息隐藏、接口隔离、热插拔 |
| 安全性 | 审计日志、最小权限、纵深防御、输入校验 |

**微服务治理五件套**：注册发现、配置中心、熔断降级、限流、链路追踪。

**雪崩链路（经典问答）**：单点超时 → 线程池耗尽 → 级联失败 → 雪崩。
对策：**超时控制 + 熔断器（半开探测）+ 舱壁隔离（线程池/信号量隔离）+ 限流 + 降级兜底**。

**MQ侧特有治理**：死信队列、重试次数上限、幂等消费、积压扩容转发、背压。

**ES侧特有治理**：副本分担读、节点角色分离、ILM冷热迁移、集群不红黄运行、脑裂防范（Master奇数台独立部署）。

#### 维度4｜性能优化与容量规划

**覆盖方向**：ES、分布式（分库分表）、大模型、云原生。

**通用分析框架（四层定位法）**：
> **接入层 → 应用/协调层 → 存储/分片层 → 资源层（CPU/内存/磁盘/网络/JVM Heap）**

每一层都要能说出：瓶颈表现、定位手段、优化动作、副作用。

**各方向标志性考点**：

| 方向 | 核心机制 | 优化手段 |
|:---|:---|:---|
| **ES** | 倒排索引、Refresh/Flush/Merge、全局归并深分页 | filter缓存、routing裁剪、_source精简、search_after/scroll、冷热分层、Heap≤32G |
| **数据库** | B+树、主从延迟、分片路由失效 | 读写分离、分库分表（水平/垂直）、异构索引表/ES补跨分片查询、汇总表 |
| **大模型** | 首Token延迟、Token成本 | 语义缓存、模型路由、KV/Prefix Cache、流式输出、上下文压缩、量化 |
| **云原生** | Pod调度、HPA | HPA/VPA、资源requests/limits、亲和性、无状态化、镜像分层缓存 |
| **Web高并发** | 分层抗压 | CDN→负载均衡→应用集群→缓存→读写分离 |

**容量公式（ES分片为例，要会算）**：
`总存储 = 原始数据 × 压缩率 × (1 + 副本数)`；`分片数 = 总存储 ÷ 目标单分片大小(20~50GB)`；且主分片数创建后不可改。

#### 维度5｜安全、权限与合规

**覆盖方向**：大模型、微服务、分布式、云原生。

**近年升温最快**，且往往是拉开分差的“隐性采分点”。

| 主题 | 必答要点 |
|:---|:---|
| **零信任** | 从不默认信任、持续验证、最小权限、微隔离、身份为新的边界 |
| **RAG权限越权** | 权限必须**下沉到检索层**（Pre-filter + Post-filter双重校验），身份由网关透传，不能依赖模型自律；上下文最小化 + 敏感字段脱敏 + 三元组审计日志 + Prompt Injection红队测试 |
| **数据安全** | 《数据安全法》《个人信息保护法》、分类分级、脱敏、加密传输与存储、留存期限、跨境限制 |
| **生成式AI合规** | 《生成式人工智能服务管理暂行办法》、算法备案、训练数据合法性、内容标识/水印、人工审核兜底 |
| **信创** | 国产CPU/OS/DB/中间件适配、双轨并行、灰度切换、回滚预案 |

#### 维度6｜可观测性与运维

**覆盖方向**：云原生、微服务、MQ、ES、大模型。

**三大支柱（要能说清各自管什么、缺了会怎样）**：

| 支柱 | 代表技术 | 回答的问题 |
|:---|:---|:---|
| Metrics（指标） | Prometheus + Grafana | “系统现在健康吗？趋势如何？” |
| Logging（日志） | ELK/EFK | “具体发生了什么？” |
| Tracing（链路） | **Jaeger** / SkyWalking / OTel | “请求卡在哪一环？依赖关系是什么？” |

**Jaeger 核心模型**：Trace（全局TraceID）→ Span（工作单元，有起止时间/标签/日志）→ SpanContext（跨进程传播）。架构：Client SDK → Agent(UDP) → Collector → Storage(ES/Cass) ← Query ← UI。

**趋势提示**：OpenTelemetry 是统一采集标准，Jaeger/Zipkin 已全面兼容 OTLP。新项目应写“用 OTel 采集，后端可选 Jaeger/Tempo”。

**异步化的可观测性代价（高频论述）**：引入MQ后调用链断裂、错误难以定位、事务边界模糊、调试困难。**对策**：TraceID 透传进消息 Header、统一日志规范、消息审计表、端到端监控大盘、死信告警。

#### 维度7｜架构评估、演进与迁移

**覆盖方向**：微服务、云原生、所有方向的“改造类”题目。

**ATAM（架构权衡分析方法）——案例题常客**：
- 四阶段流程：介绍→业务驱动→架构视图→效用树构建→场景评估→结果报告；
- **效用树四层结构**：属性 → 细化属性 → 刺激 → 响应与度量（例：性能→延迟→大促峰值下单→95%请求2秒内响应）；
- **敏感点**：影响**单一**质量属性的架构决策（如加密算法选择影响安全性）；
- **权衡点**：同时影响**多个**质量属性的决策（如加密提升安全性但降低性能）；
- **风险点 / 非风险点**。

**迁移演进题的万能骨架**：
> 现状诊断 → 目标架构 → **双轨并行/灰度发布**（按业务线或流量比例逐步切）→ 数据同步与对账 → **回滚预案** → 效果验证指标 → 老系统下线

### 四、通用答题骨架（考场上默写）

遇到任何“系统出现XX问题，请设计方案”的题目，按这个五步结构写，结构分基本拿满：

```
① 问题定位：指出瓶颈所在层级与根本机制原因（不要只描述现象）
② 方案选型：给出判据 + 对比 + 结论（为什么选它、为什么不选别的）
③ 详细设计：流程图/分层图 + 关键步骤说明（序号化）
④ 异常与兜底：幂等/补偿/重试/死信/降级/回滚（体现闭环思维）
⑤ 验证与治理：监控指标、压测、黄金测试集、演练、审计
```

**三个加分习惯**：
1. 每个优化都写明**副作用**（如“调小 refresh_interval 会提升实时性但降低写入吞吐”）；
2. 每个方案都给出**兜底**（“若该方案失效，则……”）；
3. 每条理由都**引用题干数据**（“日均8TB”“P95≤3s”“180天留存”）。

### 五、跨领域通用原理（一个原理，多处得分）

| 原理 | 出现的方向 | 一句话表述 |
|:---|:---|:---|
| **幂等** | MQ、分布式、大模型工具调用 | 同一操作执行多次与执行一次效果相同；靠唯一键+去重表/状态机/乐观锁 |
| **背压** | MQ、流式计算、微服务 | 消费者按自身处理能力向上游反馈额度，生产者额度耗尽则暂停/缓冲/降级 |
| **分层 + 就近处理** | Web高并发、云原生、ES | CDN→LB→应用→缓存→DB；越靠近用户/越廉价的层承担越多流量 |
| **异步解耦 + 削峰** | MQ、大模型推理、日志 | 用持久化队列把同步调用链切成独立伸缩单元，峰值由队列吸收 |
| **缓存（多级）** | 数据库、ES、大模型 | 本地→分布式→源站；注意穿透/击穿/雪崩及一致性策略 |
| **索引/预计算** | DB、ES、大模型RAG | 用空间换时间：物化视图、汇总表、Segment、社区摘要 |
| **冗余消除单点** | 可用性战术、ES、K8s | Master奇数台、副本、多可用区、无状态化水平扩展 |
| **最终一致性 + 补偿** | 分布式事务、Saga、ILM、Agent | 不强求瞬时一致，靠重试/对账/人工干预收敛 |
| **权限下沉** | 零信任、RAG、微服务网关 | 鉴权在数据最近处做，不在展示层或模型层做 |
| **可观测性透传** | Jaeger、MQ、异步架构 | TraceID/用户身份必须穿过进程、队列、线程边界 |

### 六、易混概念对照表（专治张冠李戴）

| 易混对 | 区分要点 |
|:---|:---|
| **缓存穿透 / 击穿 / 雪崩** | 穿透=查不存在的数据（布隆过滤器/空值缓存）；击穿=热点key过期（互斥锁/永不过期）；雪崩=大量key同时过期或Redis宕机（随机过期时间/集群高可用/限流） |
| **聚合 vs 组合（UML）** | 聚合=空心菱形弱拥有(has-a)；组合=实心菱形强拥有(part-of，同生共死) |
| **include vs extend（用例图）** | include=必须执行的公共子功能；extend=可选扩展行为；方向别反 |
| **序列图 vs 通信图** | 序列图看时间（纵向位置），通信图看空间（消息序号嵌套编号） |
| **水平分片 vs 垂直分片** | 水平=按行拆；垂直=按列/按业务拆 |
| **敏感点 vs 权衡点** | 敏感点影响一个属性；权衡点影响多个属性 |
| **search_after vs scroll** | search_after=无状态游标适合无限滚动；scroll=快照适合全量导出；都不支持跳页 |
| **RAG vs 微调** | RAG管“知识新不新、对不对”；微调管“说得像不像、格式对不对” |
| **Pull vs Push（MQ消费）** | Pull=消费者自控节奏天然背压；Push=服务端推易压垮消费者 |
| **CP vs AP** | CP=宁可拒绝请求也要返回最新值；AP=宁可返回旧值也不拒绝请求 |

### 七、硬知识速记（数字类，背了就有分）

| 项 | 值 |
|:---|:---|
| ES 单分片建议大小 | 20~50GB（日志场景可放宽至80GB） |
| ES Heap | ≤ 物理内存50%，**绝对不超过32GB**（指针压缩临界） |
| ES Refresh 默认 | 1s（近实时的来源）；Flush 约30min |
| ES Master 节点 | **奇数台（≥3）、独立部署、不参与数据存储** |
| 分片数上限经验值 | 每节点 ≤ 1000，且与 Heap 成正比 |
| 缓存过期时间 | 加随机抖动防雪崩 |
| 全年可用性 99.95% | ≈ 年停机 ≤ 4.4小时 |
| 熔断器三态 | 关闭 → 打开 → **半开**（探测恢复） |
| 消息队列 ACK | 至少一次投递 + 幂等消费 = 最终不重不漏 |
| Kafka 防丢失 | acks=all + 持久化 + 副本 |
| RAG 切片 | 中文 300~800字，重叠 50~100字 |
| 大模型 P95 优化 | 流式输出 + KV/Prefix Cache + 语义缓存 + 模型路由 |

### 八、场景关键词 → 技术点映射（读题干秒反应）

| 题干出现 | 立刻想到 |
|:---|:---|
| “任意一个下游失败导致整个请求失败” | 同步调用链脆弱 → 异步解耦 / 熔断降级 / 舱壁隔离 |
| “促销开场流量暴增打垮下游” | 削峰填谷 → MQ + 限流 + 弹性扩缩容 |
| “订单成功但积分没加” | 分布式事务 → 可靠消息最终一致性（本地消息表/事务消息） |
| “消息被重复消费” | 幂等设计（唯一键+去重表/状态机） |
| “队列积压千万条” | 扩容Queue+转发Topic、批量消费、降级丢弃、死信隔离 |
| “跨机房数据不一致” | CAP选型、主从延迟、读写路由策略 |
| “客服查订单很慢” | 分库分表路由失效 → 映射表/全局索引/ES异构索引 |
| “需要溯源、制度频繁更新” | RAG（不能只靠微调） |
| “回答可能编造” | 幻觉治理：检索提纯+拒答+引用校验+一致性判别器 |
| “不同岗位看到不同内容” | 权限下沉到检索层 Pre-filter |
| “日志量大、要全文检索” | ES 倒排索引 + 冷热分层 + ILM + 深分页改造 |
| “请求慢不知道卡在哪” | Jaeger 链路追踪 + TraceID 透传 |
| “7×24、不能有单点” | 冗余+故障检测+自动切换+多可用区 |
| “未来可能新增模块” | 微服务/DDD、水平扩展、插件化 |

### 十、考场三条铁律

1. **先判据后结论**——没有判据的选型等于没答；
